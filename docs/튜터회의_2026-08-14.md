## 2. 사고 보고 — 배치가 "성공"으로 끝났는데 캡션이 전부 비었다

### 무슨 일이 났나

캡션 모델을 Qwen3-VL-4B로 교체하기 위해 서버에서 10편을 재생성하는 배치를 걸었다.
배치는 `=== 1단계 완료 ===`를 찍고 정상 종료했다. 실제로는 **10편 중 3편만 성공**했다.

| 영상 | 결과 |
|---|---|
| dev 3편 | 재생성 성공, 빈 캡션 0건 |
| **test 7편** | **전 구간 실패 — 캡션이 빈 문자열로 덮였고, 그 상태로 색인까지 됐다** |

원인은 단순하다. **재캡셔닝에 필요한 프레임 이미지가 서버에 없었다.** 이전 실험에서
dev 3편만 올려뒀고 test 7편은 올린 적이 없다. 실패 로그가 1,525줄 쌓였다.

```
seg 0 캡션 실패: FileNotFoundError: work/panibottle_vietnam1/frames/seg_0000.jpg
```

### 왜 못 막았나 — 두 군데가 뚫려 있었다

1. **사전 검사가 절반만 있었다.** 코드는 `segments.json`에 `rep_frame` **필드가
   있는지**는 확인하지만 **그 이미지 파일이 실제로 있는지**는 확인하지 않는다.
   필드는 복사돼 있었고 이미지만 없었다.

2. **실패해도 결과를 저장한다.** 전 구간이 실패했는데도 빈 캡션을 디스크에 쓰고
   나서 종료 코드를 1로 냈다. 저장이 먼저였다.

```python
failed = caption_all(...)          # 1,525건 전부 실패
common.save_segments(...)          # ← 그래도 저장한다
if failed:
    sys.exit(1)                    # 죽는 건 저장 다음
```

### 피해와 복구

- **배포 인덱스(노트북)는 무사하다.** 11편 전부 캡션 결손 0, 프레임 전량 존재,
  무결성 해시 일치를 확인했다. 손상된 것은 서버 작업 사본뿐이다.
- 배치 직전 백업을 떠뒀기 때문에 **7편 전부 복구 가능**하다.
- 재개하려면 **test 7편의 프레임 약 1,518장을 서버에 올려야** 한다.

### 재발 방지

두 가지를 코드에 넣었다(`2e33fd0`, 실패 테스트 먼저 작성).

- 재캡셔닝 시작 전 **프레임 파일 실물 존재를 전수 확인**하고, 없으면 VLM을 적재하기도 전에 멈춘다
- **대상 전건이 실패하면 저장하지 않는다** — 중간 저장도 성공이 하나도 없으면 찍지 않는다.
  부분 실패의 기존 동작(성공분 보존 + 종료 코드 1)은 그대로 뒀다

*이 사고는 성능과 무관한 운영 결함이지만, 자동화된 배치가 "성공"을 보고할 때
그 보고를 믿을 수 있어야 한다는 점에서 방법론 문제이기도 하다.*

## 3. M8 리포트가 "요약"이 아니라는 것을 수치로 확인했다

발표 자료에 M8 산출물을 싣다가 실물을 열어봤다. 겉보기에는 문장마다 근거 구간
번호가 붙어 그럴듯한데, 재보니 **요약이라고 부르기 어렵다.**

### 측정 결과 — 리포트 4편

처음엔 1편만 보고 판단했는데, 서버에서 나머지 3편을 더 받아 4편으로 다시 쟀다.

| 영상 | 구간 | 문장 | 영상 커버 | 인용폭 | 인용당 글자 | 몰아쓰기 문장 |
|---|---|---|---|---|---|---|
| itsub_viral_gadgets | 191 | 127 | 88.5% | 1.4 | 49.7 | 3 |
| kheritage_grave_excavation | 192 | 93 | 75.5% | 1.7 | 34.7 | 1 |
| panibottle_vietnam1 | 262 | 58 | **32.4%** | 2.1 | 18.0 | 0 |
| yunnamnopo_tongyeong | 357 | 28 | 86.0% | **40.1** | **9.3** | **9** |

**네 편 다 요약에 실패하는데 방식이 둘이다.**

- **나열형 3편** — 구간을 거의 1:1로 훑는다. 문장당 인용 1.4~2.1구간, 인용이 96~100%
  시간순이다. 묶는 동작 자체가 없다. 어미도 34%가 "…이 보입니다"로 같고 존댓말과
  평어가 섞인다.
- **몰아쓰기 1편** — 28문장으로 86%를 덮어 압축된 것처럼 보이지만, **한 문장이
  70구간을 인용하면서 본문은 20자**다. 인용당 글자수가 9.3으로 다른 편의 1/4이다.

*인용 폭만 보면 마지막 편이 가장 요약처럼 보인다. 인용당 글자수를 함께 보지 않으면
몰아쓰기를 개선으로 오독한다 — 지표를 짝으로 써야 한다는 걸 이번에 배웠다.*

### 절단 원인 규명 완료 — 캡션 속 한자 2글자였다

panibottle의 커버 32.4%는 **생성 상한 문제가 아니었다.** 출력이 3,261자, 상한
16,384토큰의 **1/5 수준에서 스스로 끝났다.**

원인은 장면 설명 캡션 1건에 섞인 한자 두 글자다.

```
seg 88 캡션 :  "비행기 내부에서 파란색 좌석에 헤드靠垫이 달린 좌석들이 …"
리포트 출력 :  "… 파란색 좌석에 헤드靠垫的图片未加载成功，请稍后再试或检查网络连接。"  [종료]
```

리포트 모델이 `靠垫`을 만난 지점에서 **중국어로 전환**해 "이미지 로드 실패, 나중에
다시 시도하세요" 류의 문장을 뱉고 생성을 끝냈다. 같은 일이 **중간 단계와 최종 단계에서
두 번** 일어나, 중간 단계에서 seg 88~109가 통째로 빠지고 최종 커버가 32.4%가 됐다.

### 이게 왜 이 영상만의 문제가 아닌가

오염 캡션 필터(`is_corrupted_caption`)는 한자·가나가 **3글자 이상**이어야 잡는다.
2글자는 통과한다.

| 항목 | 값 |
|---|---|
| 전 인덱스 세그먼트 | 2,568 |
| 필터를 **통과하는** 1~2글자 혼입 캡션 | **183건 (7.13%)** |

11편 전부에 분포한다. 즉 **어느 영상에서든 재현될 수 있는 상태**다. 이 사실은
이번에 리포트를 열어보기 전까지 몰랐다.

*진단 도구는 `docs/probes/m8_report_quality.py`로 저장했고 GPU를 쓰지 않는다.*

### 발표 자료에는 어떻게 실었나

**개선 예정 단계로 명시했다.** 슬라이드 제목을 "M8 현재 출력 — 근거는 붙지만 아직
'요약'이 아니다"로 바꾸고, 위 측정치를 그대로 실었다. 잘 되는 것(근거 구간 인용)과
안 되는 것을 나눠 적었다.

**M9 채점 수치는 싣지 않았다.** 그 수치를 낸 판정자(Qwen2.5-7B)가 사전 게이트에서
탈락한 계측기이기 때문이다(직전 회의 §6). 판정 방식과 게이트 결과만 남겼다.

**척도를 먼저 고정한 이유**가 있다. 프롬프트를 고친 뒤에 지표를 정하면 결과를 보고
기준을 맞추게 된다. GPU가 없는 지금이 정할 때였다.

사전 등록하면서 함정을 하나 발견했다. **저장된 리포트 4편이 전부 test 영상이다.**
이걸 보면서 프롬프트를 고치면 test 산출물에 맞춰 튜닝하는 것이 된다. 질의·라벨을
쓰지 않으니 M9식 접촉은 아니지만 "test를 보고 설정을 고르는" 행위라는 점은 같다.
그래서 **프롬프트 개정과 판정은 dev 3편에서만** 하고, 4편은 현행 상태 기록으로만
쓰기로 문서에 못 박았다. 이 절이 없었으면 M8 쪽에서 튜닝 0회가 깨질 뻔했다.

### 4-2. 서버 GPU 확보 후 (약 4.5시간, 순서 고정)

**사전에 고정한 판정 규칙 중 가장 중요한 것:** 새 설정의 test 수치가 기존보다 낮게
나와도 **채택을 철회하지 않는다.** 철회하면 test로 고르는 것이 되어 "튜닝 0회"가
깨진다. 그 경우 "독립 표본에서는 이겼으나 최종 평가에서는 재현되지 않았다"로 보고한다.

- **8/10은 커밋이 23건으로 가장 많았지만 토큰은 1.5M으로 적다.** GPU 배치를
  돌려놓고 기다린 날이기 때문이다. 토큰 사용량과 진척은 비례하지 않는다.
- 도구 호출 14,523건 중 절반 이상이 명령 실행(7,776건)이다. 코드를 쓰는 것보다
  **돌려보고 확인하는 데** 더 많이 썼다.

## 6. 튜터께 여쭙고 싶은 것

1. **M8을 어디까지 고칠 것인가.**
   절단은 원인이 밝혀졌으니 고치면 된다. 문제는 **"요약답게 묶는 것"**이다. 네 편
   중 셋은 아예 안 묶고, 하나는 번호만 몰아 붙인다. 이게 **프롬프트로 되는 일인지,
   map-reduce 분할 방식 자체를 바꿔야 하는 일인지** 판단이 필요하다.

2. **M8 품질을 무엇으로 잴 것인가.**
   §3의 지표(압축률·인용 폭·인용당 글자수·문체 반복)는 제가 이번에 만든 것이라
   표준이 아니다. ROUGE 같은 통상 척도를 안 쓴 이유는 **정답 요약문이 없어서**인데,
   사람이 쓴 기준 요약을 몇 편 만들어 두는 편이 나은지 조언을 구한다.

3. **오염 필터 임계를 낮출 것인가.**
   지금은 한자·가나 3글자 이상만 오염으로 본다. 2글자를 잡도록 낮추면 183건이
   재생성 대상이 되는데, 그중에는 정당한 표기도 섞여 있을 수 있다. 다만
   **재생성은 자동 판정분만** 한다는 원칙은 그대로 유지된다. 임계를 낮출지,
   아니면 **리포트 입력 시점에서만 제거**하고 인덱스는 두는 쪽이 나은지 판단이
   필요하다. 현재 계획은 후자다(인덱스를 건드리면 재평가 절차가 따라온다).

4. **직전 회의 §7의 3번이 아직 미결이다.**
   6GB 제약이 풀려 8B·14B·32B가 후보가 될 수 있다. **독립 확증을 통과한 4B로
   마무리할지, 더 큰 모델까지 볼지** 판단이 필요하다. 남은 기간을 고려하면
   4B로 확정하고 M8·Phase 4에 시간을 쓰는 쪽이 나아 보인다.

5. **이번 배치 사고를 보고서에 어떻게 쓸 것인가.**
   성능과 무관한 운영 결함이지만, "자동 배치가 성공을 보고했는데 실제로는 산출물이
   파괴됐다"는 사례라 재현성 관점에서는 기록할 가치가 있다고 본다. 다만 최종
   보고서에 넣을 성격인지는 판단이 필요하다.

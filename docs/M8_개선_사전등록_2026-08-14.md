# M8 리포트 개선 — 판정 기준 사전 등록 (2026-08-14)

**이 문서는 M8 프롬프트·구조를 손대기 전에 작성한다.** 아래 임계값은 개선 후
수치를 보기 전에 정했다. 착수 전 커밋하고, 커밋 이후 임계값을 고치지 않는다.

근거 데이터: `docs/probes/_scratch/m8_report_quality.json`
(생성: `python docs/probes/m8_report_quality.py`, GPU 미사용 — 저장된 산출물만 읽는다)

---

## 0. 왜 지금 정하는가

서버 GPU가 없어서 M8을 다시 돌릴 수 없다. **그래서 지금이 기준을 정할 때다.**
프롬프트를 고친 뒤에 "무엇이 개선인가"를 정하면 결과를 보고 기준을 맞추게 된다.

## 1. 현재 상태 (개선 전 기준선)

저장된 리포트 4편. 전부 Qwen2.5-7B-Instruct · 분할 60구간 · 겹침 5.

| 영상 | 구간 | 문장 | 영상 커버 | 인용폭 | 인용당 글자 | 몰아쓰기 문장 | 인용 순차 |
|---|---|---|---|---|---|---|---|
| itsub_viral_gadgets | 191 | 127 | 88.5% | 1.4 | 49.7 | 3 | 98% |
| kheritage_grave_excavation | 192 | 93 | 75.5% | 1.7 | 34.7 | 1 | 96% |
| panibottle_vietnam1 | 262 | 58 | **32.4%** | 2.1 | 18.0 | 0 | 100% |
| yunnamnopo_tongyeong | 357 | 28 | 86.0% | **40.1** | **9.3** | **9** | 73% |

**네 편 모두 요약에 실패하는데, 방식이 두 가지다.**

- **나열형** (itsub·kheritage·panibottle): 구간을 거의 1:1로 훑는다. 문장당 인용
  1.4~2.1구간, 인용이 96~100% 시간순이다. 묶는 동작 자체가 없다.
- **몰아쓰기형** (yunnamnopo): 28문장으로 86%를 덮지만 **한 문장이 70구간을
  인용하면서 본문은 20자**다. 인용당 글자수가 9.3으로 다른 편의 1/4~1/5이다.
  압축된 것처럼 보이지만 내용이 없다.

*인용 폭만 보면 yunnamnopo가 가장 요약처럼 보인다. 인용당 글자수를 함께 보지
않으면 몰아쓰기를 개선으로 오독한다 — 그래서 두 지표를 짝으로 쓴다.*

### 절단 — 원인 규명 완료

panibottle의 커버 32.4%는 생성 상한 문제가 **아니다.** reduce 출력이 3,261자
(상한 16,384토큰의 1/5 수준)에서 스스로 끝났다.

원인은 **캡션 1건의 한자 2글자**다.

```
seg 88 캡션:  "비행기 내부에서 파란색 좌석에 헤드靠垫이 달린 좌석들이 …"
리포트 출력:  "… 파란색 좌석에 헤드靠垫的图片未加载成功，请稍后再试或检查网络连接。" [종료]
```

리포트 모델이 `靠垫`을 만난 지점에서 중국어로 전환해 "이미지 로드 실패" 류의
문장을 뱉고 EOS를 냈다. **같은 일이 map 청크1과 reduce에서 두 번** 일어났다.

- map 청크1은 seg#55~114를 맡았는데 seg#87에서 끝났다 → **seg 88~109가 어느
  청크에도 없다**
- reduce는 seg#0~87까지만 쓰고 끝났다 → 최종 커버 32.4%

`common.is_corrupted_caption`은 한자·가나가 **3글자 이상**이어야 잡는다. 2글자는
통과한다.

### 노출 규모

| 항목 | 값 |
|---|---|
| 전 인덱스 세그먼트 | 2,568 |
| 오염 필터를 **통과하는** 1~2글자 혼입 캡션 | **183건 (7.13%)** |

특정 영상에 몰려 있지도 않다 — 11편 전부에 있고, `_10_000`이 50건으로 가장 많다
(`フラ`가 반복 등장). 즉 이 종료 사고는 panibottle만의 우연이 아니라 **어느
영상에서든 재현될 수 있는 상태**다.

## 2. 무엇을 바꿀 것인가 (착수 전 명시)

| # | 변경 | 성격 |
|---|---|---|
| 1 | 리포트 입력 캡션에서 잔여 한자·가나 제거 | **결함 수정** |
| 2 | map 청크가 담당 구간을 다 덮지 못하면 감지·재생성 | **결함 수정** |
| 3 | 요약 프롬프트 개정 — 구간 나열이 아니라 장면 단위로 묶기 | 품질 개선 |
| 4 | 몰아쓰기 억제 — 인용당 최소 서술량 규칙 | 품질 개선 |
| 5 | 문체 통일 (존댓말/평어 택일) | 품질 개선 |

**바꾸지 않는 것:** 분할 크기(60)·겹침(5)·리포트 모델(7B)·인용 표기 형식.
분할 크기는 한 번도 변형해본 적이 없어 별도 실험 대상으로 남긴다.

### 1번을 어떻게 할 것인가 — 두 경로

`config.yaml`에 `caption_normalize_cjk: false`가 이미 있다. 이걸 켜면 캡션 자체가
바뀌므로 **재임베딩과 test 재평가 절차가 따라온다**(8-3(c) 기재 사항).

리포트 절단만 막는 것이 목적이면 **M8 입력에서만** 제거하는 편이 부작용이 없다.

**선택: M8 입력 시점에서만 제거한다.** 인덱스와 검색 결과는 건드리지 않는다.
`caption_normalize_cjk`를 켜는 것은 8회차 재평가와 묶어 별도로 판단한다.

## 3. 판정 기준 (결과 보기 전 확정)

### 3-1. 필수 관문 — 하나라도 실패하면 미채택

| 관문 | 기준 | 근거 |
|---|---|---|
| G1 커버 | **전 영상 `coverage_of_video` ≥ 0.90** | 현행 최저 32.4% |
| G2 절단 | `truncated_tail` 없음 **그리고** `truncation.stage != "reduce"` | 조기 종료 재발 차단 |
| G3 몰아쓰기 | **`cite_dump_sentences` == 0** 그리고 `chars_per_cite_mean` ≥ 15 | 현행 yunnamnopo 9건·9.3자 |

*G3의 두 조건은 짝이다. 하나만 보면 몰아쓰기를 압축으로 오독한다.*

### 3-2. 주 지표

**`sentences_per_covered_segment` ≤ 0.35** — 커버한 구간 수 대비 문장 수.

현행: itsub 0.75 · kheritage 0.64 · panibottle 0.68 · yunnamnopo 0.09(몰아쓰기).
나열형 3편의 평균이 0.69이므로 **절반 이하**를 목표로 잡는다.

*yunnamnopo의 0.09는 G3에서 걸러지므로 이 목표의 기준선에서 제외한다.*

### 3-3. 부가 지표 (판정에는 쓰지 않고 병기한다)

- 문체 통일: `n_polite`와 `n_plain` 중 한쪽이 전체의 95% 이상
- 어미 반복: `top_ending_ratio` ≤ 0.25 (현행 panibottle 0.34)
- 인용 순차성: 100%에서 내려오는지 (요약이면 되돌아오는 문장이 생긴다)

### 3-4. 성공/실패 서술

| 결과 | 서술 |
|---|---|
| G1~G3 통과 + 주 지표 달성 | 개선 채택 |
| G1~G3 통과, 주 지표 미달 | **결함은 고쳤으나 요약성은 개선하지 못했다**고 적는다 |
| 관문 실패 | 미채택. 어느 관문에서 왜 걸렸는지 기록 |

**나쁘게 나와도 지표를 바꾸지 않는다.** 목표 0.35가 과했다고 판단되면 그 판단
자체를 결과와 함께 기록하고, 임계는 이 문서 그대로 둔다.

## 4. 어디서 튜닝할 것인가 — 이게 가장 중요하다

**§1의 리포트 4편은 전부 test 영상이다.** 이걸 보면서 프롬프트를 고치면 test
산출물에 맞춰 튜닝하는 것이 된다. 질의·라벨을 쓰지 않으니 M9식 접촉은 아니지만,
**test 자료를 보고 설정을 고르는 행위**라는 점은 같다.

따라서:

- **프롬프트 개정과 임계 판정은 dev 3편에서 한다.** dev 리포트를 새로 생성해
  기준선을 다시 잡고, 그 위에서 개선안을 비교한다.
- **§1의 4편은 "현행 상태 기록"으로만 쓴다.** 결함의 존재와 규모를 보이는 용도이며,
  개선안 선택에 쓰지 않는다.
- 개선안이 dev에서 관문을 통과한 뒤, test 영상 리포트는 **8회차 재평가에서 한 번만**
  재생성한다(프로토콜 §2 7번 단계).

*이 절이 없으면 "test 리포트를 보고 프롬프트를 고쳤다"가 되어, 지금까지 지킨
튜닝 0회가 M8 쪽에서 깨진다.*

### dev 기준선이 없다는 한계

현재 dev 3편의 M8 리포트가 저장돼 있지 않다. GPU 확보 후 **개선 전 dev 리포트를
먼저 생성**해 기준선을 잡고, 그다음에 개선안을 돌린다. 순서를 바꾸면 비교 대상이
없다.

## 5. 실행 순서

```
GPU 없이 (지금)
  1. 진단 프로브 확정                       docs/probes/m8_report_quality.py   [완료]
  2. 이 문서 커밋                                                              [진행]
  3. M8 입력 CJK 제거 구현 + 테스트 (TDD)
  4. map 청크 커버 미달 감지 구현 + 테스트 (TDD)

GPU 확보 후
  5. dev 3편 개선 전 리포트 생성 → 기준선
  6. 개선안 적용 후 dev 3편 재생성 → §3 관문·주 지표 판정
  7. 통과 시에만 test 재생성(8회차 재평가에 포함)
```

## 6. 이 문서의 한계

- 표본이 리포트 4편이고 전부 같은 모델·같은 분할이다
- 요약 품질 지표는 이 과제용으로 만든 것이며 표준 척도가 아니다. 통상적인 요약
  평가(ROUGE 등)를 쓰지 않는 이유는 **정답 요약문이 없기** 때문이다 — 사람이 쓴
  기준 요약을 만들면 그쪽이 더 낫다. 튜터 의견을 구할 항목이다
- 임계값(0.90 / 0.35 / 15자)은 현행 수치에서 역산한 것이지 외부 근거가 없다.
  근거가 약하다는 점을 결과와 함께 적는다

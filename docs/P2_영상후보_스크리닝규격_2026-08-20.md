# P2 신규 영상 후보 — 스크리닝 규격 (2026-08-20)

**이것은 자료 평가가 아니라 자원 조사다.** 영상 후보를 훑는 것은 P2 결과를 보는 것이
아니므로 선택 편향을 만들지 않는다. `k` 확정·라벨링·인덱싱은 계속 HOLD다.

## 0. 스크리닝은 **재생 시간만으로 끝난다**

`seg_len_sec = 5`이므로 세그먼트 수는 재생 시간에 정비례한다.

```
목표 세그먼트   150 ~ 400
= 재생 시간     750초 ~ 2,000초  =  **12분 30초 ~ 33분 20초**
```

> **인덱싱하지 않고 재생 시간만 보고 걸러낼 수 있다.** GPU를 쓰기 전에 pool을 다
> 만들 수 있다는 뜻이다.

경계 참고 — dev의 `gwaktube`는 149세그(12분 25초)로 **목표 범위 바로 아래**다.
목표 범위는 dev와 겹치는 구간이고 dev를 재현하는 것이 아니다(P2 사전등록 보충2 §2-1).

## 1. 포함 기준 — 사전등록 보충2 §3-2 그대로

```
필수  재생 시간 12분 30초 ~ 33분 20초
필수  한국어 발화 포함 (STT 산출이 나와야 자막 채널이 생긴다)
필수  dev 3편 · test 4편에 쓰인 영상이 아님
      dev  _10_000_… · kheritage_grave_excavation · gwaktube_soviet_apartment
      test panibottle_vietnam1 · gemini_promo · yunnamnopo_tongyeong · itsub_viral_gadgets
권장  화면 내용이 발화와 다른 구간이 있는 영상 — 캡션 채널이 기여할 여지가 있다
```

**"권장" 항목을 선택 기준으로 강하게 쓰지 마라.** 캡션이 유리한 영상만 모으면 표본이
후보 모델에 유리해진다. **재생 시간과 한국어 발화만 hard 기준이다.**

## 2. 이미 확보된 것

| 상태 | 세그먼트 | 재생 시간 | 영상 |
|---|---|---|---|
| FREE | 183 | 15.2분 | `baekmansonghee_jirisan` |
| FREE | 211 | 17.6분 | `jissi_farm` |
| FREE | 395 | 32.9분 | `pland_costco_hosting` |
| FREE | 192 | 16.0분 | `softyeon_ceramics` |

**4편. 전부 범위 안이고 이미 인덱싱돼 있다.** 즉 이 4편은 GPU 비용이 캡션 생성분만
남아 있다(2 arm 동시 생성).

## 3. `k`별 추가 확보 목표

| `k` | 추가 필요 | 누적 GPU (≈2h/편, 신규분만) |
|---|---|---|
| 8 | 4편 | ~8h |
| 16 | 12편 | ~24h |
| 24 | 20편 | ~40h |
| 53 | 49편 | ~98h |

GPU 시간은 `gpu-batch` 스킬 실측 속도에서 환산한 **계획값**이다. 이 구성에서 실측한
값이 아니다.

## 4. pool 작성 형식

`docs/probes/_scratch/p2_video_pool.csv`에 후보를 모은다. **gitignore 대상이라
저장소에 올라가지 않는다.**

```csv
title,duration_sec,est_segments,korean_speech,source,eligible,note
```

`est_segments = ceil(duration_sec / 5)`, `eligible = 750 <= duration_sec <= 2000`.

**pool을 다 만든 뒤에 `k`를 고른다.** 확보 가능한 편수를 모르는 상태로 `k`를
확정하면 그 숫자가 자원 한도와 어긋난다.

## 5. `k` 선택은 통계가 아니라 자원 결정이다

```
16   구조는 가장 가까운 dev scaling. 다만 k=3 기반이라 매우 불안정
53   194-cluster 기반으로 scaling은 안정적이나 구조가 다름
24   두 근거 사이의 타협 — **별도의 통계적 근거가 생긴 숫자가 아니다**
```

> **"중간값처럼 보인다"는 이유로 24를 고르지 않는다.**

자원 제약이 없다면 **53을 보수적 planning value로 택하는 것**이 합리적이다. 53이
필요하다고 증명된 것은 아니지만 두 스케일링의 상단이고, `half-width > 0.04 → 판정
불가`로 끝날 위험을 덜 감수한다. **49편 확보와 477질의가 현실적으로 크다면, 통계가
아니라 자원 한도를 근거로 더 작은 `k`를 고정한다** — 그 사유를 승인 문서에 적는다.

## 6. 확정 후 순서

```
1  pool 작성 (재생 시간만으로 스크리닝)
2  [승인 ①] k · 영상당 질의 수 · 층별 목표를 별도 문서로 커밋
3  [승인 ②] M1~M4 인덱싱 PLAN → CANARY → FULL
4  2 arm 캡션 동시 생성 (같은 하드웨어·commit·경로)
5  라벨 (허용 도구만: label_contact_sheet · label_intake)
6  P2 실행 · 한 번만 평가
```

**`k`를 freeze한 뒤에는 부족해 보여도 중간 결과를 보고 늘리지 않는다.** 늘리려면 새
사전등록 + 결합 분석 명시다(보충2 §4-2).

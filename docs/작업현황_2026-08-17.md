## 3. 사고 3건 — 전부 실행 절차, 연구 결과 오염 없음

| 사고 | 원인 | 손실 |
|---|---|---|
| 유령 프로세스 대기 | 대기 조건 `pgrep -f`가 **자기 런처 셸**까지 매칭 | GPU 8.5시간 유휴 |
| 배타 플래그 | `--captions-only --force` 동시 지정 | 배치 즉시 종료 |
| 편집본 ≠ 실행본 | `/tmp`가 git-bash와 Windows 파이썬에서 다르게 해석됨 | C1 보강 단계 누락 |

세 번째가 가장 위험하다 — **"고쳤다고 생각한 코드"와 "서버가 실행한 코드"가 달랐다.**

**같은 실수를 오늘 한 번 더 했다.** 배치 완료 대기 스크립트가 거짓 실패를 보고했다.
원인 둘:

1. `grep -c ... || echo 0` — `grep -c`는 0건일 때 "0"을 찍고 **exit 1**을 낸다.
   `||`가 한 번 더 찍어 출력 줄이 밀렸고, **줄 위치로 파싱**해서 여분의 `0`을
   프로세스 수로 읽었다 → 라벨 파싱으로 교체
2. 단발 관측으로 실패 선언 — 배치는 `for` 루프라 **영상 사이 순간엔 python이 없다**
   → 프로세스 부재 + 로그 정체가 **연속 3회**여야 실패로 센다

세 번째 결함도 같이 고쳤다: `pgrep` 패턴을 `^/ssd/.../python`으로 앵커해 자기매칭을
막았다(앵커 전 count=2, 후 count=1).

**교훈은 같다.** 즉석 shell 파이프라인에서 exit code 의미와 프로세스 매칭을 반복해서
틀린다. 연구 규율은 주의사항이 아니라 **코드 검사**로 옮겨야 한다 — P0가 그 예다.

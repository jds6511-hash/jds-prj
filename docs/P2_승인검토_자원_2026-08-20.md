# P2 승인 ① 검토 자료 — 자원과 scaling 근거 (2026-08-20)

**이 문서는 `k`를 고르지 않는다.** 사용자가 승인할 수 있도록 **선택지와 근거를
결과 보기 전에 정리**한 것이다. `k`를 확정하면 별도 문서로 커밋한 뒤 표집을 시작한다
(`부호역전_확증_보충2_P2설계_2026-08-20.md` §9 승인 지점 ①).

관련: P2 사전등록 `98de...` 계열 — 본 사전등록(`98d4efa`) · 보충1(`cb16697`) ·
보충2(`58de1bf`).

## 0. 확인해야 할 세 가지 — 사용자가 지정한 항목

```
1  k별 예상 human-label workload
2  확보 가능한 150~400 세그먼트 영상 수
3  어떤 scaling 근거로 그 k를 **결과 보기 전에** 선택했는가
```

> 사용자가 지적한 대로 **판정 가능한 video-cluster sampling frame을 어떻게
> 확보할지까지 포함한 자원 승인**이다.

범위에 완전히 들어오지 않는다.** 목표 범위는 dev와 "겹치는" 것이고 dev를 재현하는
것이 아니다.

## 2. 노동량 지렛대 — **영상당 질의 수는 판정력을 줄이지 않는다**

판정력은 **cluster 수 = 영상 편수**가 정한다. 한 영상에서 질의를 더 뽑아도 cluster는
늘지 않는다(보충2 §2-2). 따라서 **영상당 질의 수는 cluster 수를 건드리지 않고 줄일 수
있는 유일한 비용 축**이다.

```
dev 실적       영상당 30~36 질의 (96질의 / 3편)
층 요구        query type 3종(장면형·자막형·복합형) 층별 목표 등록 필수
실용 하한      영상당 9질의 (층별 3) — 층 대표성을 유지하는 최소
```

**영상당 질의를 9로 줄이면 같은 cluster 수를 1/3 노동으로 얻는다.** 대신 영상 내
평균의 분산이 커지므로 cluster 간 분산 추정이 나빠질 수 있다 — 그 방향은 미측정이다.

## 3. `k`별 자원표

GPU 시간은 `gpu-batch` 스킬의 실측 속도(M2 ~25분/33분영상, M3 Whisper+캡션
~75분/395세그, m4 ~2분)에서 **환산한 계획값**이다. **이 구성에서 실측한 값이 아니다.**
2 arm을 같은 경로에서 함께 생성해야 하므로(CLAUDE.md 동시점 대조군) 캡션 생성이
2회다.

| `k` | 신규 영상 | 질의 @9/편 | 질의 @30/편 | GPU 시간 (≈2h/편) | 판정 가능? |
|---|---|---|---|---|---|
| 4 | 0 | 36 | 120 | 0 | **✕ 하한 미달 — 기술용만** |
| 8 | 4 | 72 | 240 | ~8h | ✕ 하한 미달 |
| **16** | **12** | **144** | **480** | **~24h** | ○ 하한 충족 |
| 24 | 20 | 216 | 720 | ~40h | ○ |
| **53** | **49** | **477** | **1,590** | **~98h** | ○ 상단 추정 |

**영상 확보 자체가 사용자 작업이다** — 한국어 발화가 있고 STT 산출이 나오는 12.5~33분
영상을 12~49편 구해야 한다.

## 4. scaling 근거 — 결과 보기 전에 고정한 것

목표는 `+0.031`(AI Hub)과 `−0.090`(dev)을 가르는 것이므로 **CI half-width ≤ 0.04**다.

| 근거 | 계산 | 필요 cluster |
|---|---|---|
| AI Hub 실측 | half-width 0.021 @ 194 cluster → `194·(0.021/0.04)²` | **≈ 53** |
| dev 실측 | half-width 0.092 @ 3 cluster → `3·(0.092/0.04)²` | **≈ 16** |

**두 추정이 3배 이상 어긋난다.** 이유는 표본 구조 차이다.

```
AI Hub  영상 194편 · 영상당 12세그 · 질의당 후보 12개 → cluster 내 분산이 작다
dev     영상 3편 · 영상당 149~314세그 · 후보 149~314개 → cluster 내 분산이 크다
```

**P2는 dev 쪽 구조에 가깝다**(150~400세그 장편). 그래서 dev 스케일링(16)이 더 관련
있어 보이지만, **cluster 3개로 추정한 분산이라 그 자체가 매우 불안정하다.**
AI Hub 스케일링(53)은 cluster 194개로 안정적이지만 **구조가 다른 표본에서 나왔다.**

> **어느 쪽도 "필요 표본 수"의 확정값이 아니다.** 16은 **그보다 작으면 판정하지
> 않는다는 하한**이고, 53은 **다른 구조의 표본에서 나온 상단 추정**이다.
> P1도 이 격차를 좁히지 못했다 — 풀 크기 효과는 확인됐지만 분산 구조를 추정할
> 설계가 아니었다.

### 4-1. 판정 규칙은 이미 고정돼 있다 — `k` 선택의 위험을 흡수한다

```
달성 half-width > 0.04  →  "이 규모로는 판정 불가"로 보고하고 멈춘다
유의성 쫓아 추가 표집 금지. 추가하면 새 사전등록 + 결합 분석 명시
k < 16이면 PRIMARY 판정 안 함 (기술용으로만 보고)
```

**이 규칙 때문에 `k`를 작게 골라도 "애매함을 차이 없음으로 바꾸는" 경로는 막혀
있다.** 작게 고르면 판정 불가로 끝날 확률이 올라가는 것이고, 그 비용은 노동량 절감과
맞바꾸는 것이다.

## 5. 선택지 정리 — 사용자 결정

| 안 | 내용 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **A** | `k=16` · 질의 9/편 | 하한 충족. 신규 12편 · 144질의 · ~24h GPU | dev 스케일링에만 의존. 판정 불가로 끝날 여지가 크다 |
| **B** | `k=24` · 질의 9/편 | 두 스케일링 사이. 신규 20편 · 216질의 · ~40h | 노동량 1.5배 |
| **C** | `k=53` · 질의 9/편 | 상단 추정 충족. 신규 49편 · 477질의 · ~98h | 노동량이 지금까지 전체 라벨 작업을 넘는다 |
| **D** | 지금은 `k` 미확정 | 신규 영상 확보 가능성부터 확인 | P2가 계속 열려 있다 |

**추천은 하지 않는다** — 노동량이 사용자 부담이고, 위 표의 어느 칸도 방법론적으로
우월하지 않다. **판정 규칙이 이미 고정돼 있어서 작은 `k`도 부정직해지지 않는다.**

## 6. `k`를 확정하면 그 다음

```
1  k · 영상당 질의 수 · 층별 목표를 별도 문서로 커밋      ← 승인 ①
2  신규 영상 확보 (사용자)
3  M1~M4 인덱싱 PLAN → CANARY → FULL 3단 승인            ← 승인 ②
4  2 arm 캡션 동시 생성 (같은 하드웨어·commit·경로)
5  라벨 작성 (허용 도구만)
6  P2 실행 · 한 번만 평가
```

## 7. 잊지 말 것

**P2 sign confirmation ≠ model adoption.**

```
P2         caption retrieval 부호 문제
I1 검증    corruption detector 배포 장벽 — 별도 트랙, 표집 완료 · 라벨 대기
```

**둘 중 하나만 통과해도 4B 채택으로 넘어가지 않는다.**

## 8. 동시에 걸린 라벨 노동량 — 같은 자원표에서 본다

```
I1 validation   프레임 83장 A 라벨 → 그중 cjk_text_present만 B 라벨
                (표집 완료. label_kit/i1_validation/labels_v.csv 대기)
P2              위 표대로 144~1,590 질의 (영상 확보가 선행)
```

**I1 쪽이 먼저 끝난다** — 83장이고 이미 시트가 준비돼 있다. P2는 영상 확보가 선행
조건이라 착수까지 시간이 걸린다. **두 작업이 경쟁하지 않는다.**

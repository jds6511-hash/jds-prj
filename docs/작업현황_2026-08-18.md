### 5-1. dev 3-arm 배치는 **배포 방식 결정의 입력**이다 (순서 정정 2026-08-18)

**앞서 "배포 방식 결정 → 배치"로 적었으나 순서를 뒤집는다.** 그 배치가 바로 결정에
필요한 정보를 만들기 때문이다. 운영상 노트북/서버를 먼저 택해야 할 사유가 없다면
배치를 **아키텍처 결정 프로브**로 본다.

```
dev 3-arm 동시점 배치 → 4bit 생존 여부 확인 → 배포 방식 최종 결정
```

| arm | 답하는 질문 |
|---|---|
| `4B/P0 bf16` | 2×2 결과가 dev에서도 재현되는가 |
| `4B/P0 4bit` | **4B를 노트북에서 쓸 수 있는가** |
| `3B/P0 4bit` | 동시점 대조군 — 현행 |

**과거 4bit 손실 −0.068은 경고이지 결론이 아니다.** 그것은 `4B/P1` 조건의 기록이고,
최종 후보군은 `P0`다. **동시점 대조군으로 다시 재는 편이 판단에 깨끗하다.**

*판정이 갈리는 방식:* 4bit에서 이득이 살면 노트북 배포 유지로 닫힌다. 죽으면
질문이 **운영 아키텍처 변경**(서버 bf16 추론)으로 바뀌고 지연·비용·가용성·fallback
경로가 같이 판정 대상이 된다. M8/M9가 이미 랩 GPU 전제이므로 "노트북 전용"은 이미
사실이 아니지만, 검색 경로(M3 캡션 생성)를 서버로 올리는 것은 별개 결정이다.

**지금 급하지 않다.** I1 프레임 라벨이라는 사람 대기열이 이미 걸려 있어, 그 사이
인프라·M8 트랙을 닫는 편이 wall-clock 효율이 높다.

### 5-5. 열람 조건을 2편으로 되올린다 (2026-08-18, FULL 승인과 함께)

|---|---|

별도 취급한다 — 그 영상의 구조 수치는 reference 대비 지표로 쓰지 않는다.

**실행 승인과 열람 승인은 분리한다.** FULL 실행은 사람이 내용을 보지 않는 한
inventory를 오염시키지 않으므로 지금 돌린다. GPU가 도는 동안 `kheritage`
inventory를 끝내는 것이 wall-clock상 이득이다.

**계획 파일은 고치지 않았다.** `m8pilot_0818d`는 `plan_hash`·
`execution_commit=d601cb9`에 묶여 완료됐다. 계획을 고치면 "실행 당시 계획"과
"현재 계획"이 갈리고, 어떤 게이트가 그 run에 적용됐는지 사후에 말할 수 없다.
대신 **별도 층**을 만들었다(`17c7bcd`).

```

  requires_frozen_inventory: [gwaktube, kheritage]   ← 계획과 **합집합**
  excluded_from_reference:    [_10_000]
```

정책은 **조일 수만 있고 풀 수 없다**(합집합). 그리고 `report_inputs`가
`RUN_COMPLETE`의 `plan_hash`를 현재 `plan_hash`와 대조한다 — 이 검사가 없었으면
계획 파일을 고쳐 **게이트를 갈아끼울 수 있었다.**

**실측 확인** — 서버에서 `gwaktube`만 동결된 상태로 `report`를 시도했다.

```
차단: 정답 사건 목록이 아직 **동결**되지 않았다: ['kheritage_grave_excavation']
exit=2
```

`excluded_from_reference`는 **선언일 뿐 아직 강제되지 않는다.** temporal 지표를
계산하는 보고 단계에서 이 목록을 읽어 분모에서 빼야 하고, 그 코드는 아직 없다.

### 5-6. 표본 소비 선언 — 열람 **직전**에 적는다 (2026-08-18)

> `gwaktube`·`kheritage`는 본 M8 dev pilot의 reference 평가에 사용되어 **이 시점부터
> 소비된 표본으로 취급한다.** 이후 metric·threshold·event-unit 규칙 변경의 **확증
> 표본으로 재사용하지 않으며**, 개별 출력 열람 후의 실패 유형 분석은 **탐색적
> 분석으로 구분한다.**

**첫 열람은 raw JSON이 아니라 고정된 estimand로 제한한다.**

```
1. exp_launcher.py report        접근 게이트 통과만 확인
2. m8_pilot_report.py 실행        사전등록 지표 산출
   ← 이 시점까지 per_video 사건 이름·경계 직접 열람 금지
3. 요약 지표를 최초 결과로 읽음
4. 저장·커밋 후에만 개별 사건 열람 (탐색적으로 명시)
```

개별 사례를 먼저 보면 "이 경우 IoU 0.3은 너무 낮다" 같은 판단이 들 수 있고, 그때는
이미 결과를 본 뒤라 threshold를 건드릴 수 없다. 순서로 막는다.

**허용되는 해석 범위** — 이 목록 밖의 주장을 하지 마라.

| 낼 수 있는 것 | |
|---|---|
| `event_temporal_alignment` | reference event 균등 macro |
| `temporal_event_recall@IoU>=0.3/0.5/0.7` | threshold 고정 |
| `timeline_span_coverage` | 생성 span만, **진단값** |
| `_10_000` | 구조 진단만 — reference 비교 없음 |

| 낼 수 없는 것 |
|---|
| CI — 영상 2편 사례 pilot |
| PASS/FAIL 판정 |
| **semantic correctness·coverage 주장** — temporal 지표는 시간 정렬만 본다 |

**semantic coverage를 새로 설계할 경우의 제약.** 이번 두 영상의 M8 `description`을
본 뒤 semantic rubric이나 judge 규칙을 만들면, **그 규칙을 같은 두 영상에서 확증하면
안 된다.** 새 8~12편이나 별도 미사용 영상으로 넘긴다.

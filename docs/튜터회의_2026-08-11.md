# 튜터 회의 자료 — 2026-08-11

**대상 기간:** 8월 8일(금) ~ 8월 11일(화) 낮
**한 줄 요약:** 캡션 모델을 바꾸면 성능이 오른다는 것을 독립 데이터에서 확인했고,
그동안 모델 교체를 막고 있던 제약이 **근거 없는 것으로 판명**됐다.

---

## 1. 배경 — 무엇이 문제였나

우리 시스템은 영상에서 장면 설명(캡션)과 음성 자막을 뽑아, 사용자의 한국어 질문에
맞는 장면을 찾아준다. 성능을 올리려면 어디를 손봐야 하는지가 계속 불분명했다.

이번 기간의 목표는 **"성능을 올릴 지렛대가 어디인가"를 하나씩 확정해서 지우는
것**이었다. 후보는 넷이었다.

| 후보 | 질문 |
|---|---|
| 음성 인식(STT) | 자막을 더 정확히 뽑으면 좋아지나 |
| 프레임 선택 | 장면 대표 이미지를 잘못 고르고 있나 |
| 캡션 모델 | 장면 설명을 만드는 모델이 약한가 |
| 임베딩 모델 | 설명과 질문을 맞추는 모델이 약한가 |

## 4. 오늘 아침의 반전 — 프로젝트 전제가 무너졌다

### 무엇을 믿고 있었나

며칠 전 측정에서 이상한 결과가 있었다. **같은 모델·같은 설정인데도 노트북에서 만든
캡션이 서버에서 만든 캡션보다 성능이 0.09 높았다.** 기계가 바뀌면 성능이 떨어진다는
뜻이다.

이걸 사실로 받아들이자 다음이 줄줄이 따라왔다.

```
노트북 캡션이 더 좋다
   → 노트북에서 생성해야 한다
      → 노트북 GPU가 6GB뿐이다
         → 큰 모델을 못 쓰고, 모델을 압축(4bit)해야 한다
            → 압축 손실 때문에 후보 모델의 이득이 사라진다
```

**결과적으로 "노트북 성능 한계가 어떤 모델을 쓸지를 결정"하는 상태**였다.

### 검증 결과 — 사실이 아니었다

제3자 데이터 97편·562건에서 같은 조건으로 다시 쟀다.

```
서버 생성 0.4872   노트북 생성 0.4826
차이 −0.0046   (95% 신뢰구간 −0.027 ~ +0.017)
```

**차이가 없다.** 그리고 이건 "못 쟀다"가 아니다. 이 표본은 0.036 크기의 차이도
검출할 수 있는데, 신뢰구간 상한이 +0.017이다. 즉 **0.09는 확실히 배제된다.**

원래 0.09가 나왔던 dev 데이터는 질의가 96건뿐이고 검출 한계가 ±0.086이었다.
**0.09는 정확히 그 노이즈 최대값 크기다.** 작은 표본에서 나온 우연을 며칠간 배포
결정의 뿌리로 쓰고 있었던 셈이다.

부수적으로 흥미로운 사실 하나 — 기계를 바꾸면 캡션 문장의 **77%가 실제로 달라진다**
(완전일치 23.2%). 그런데 **검색 성능은 달라지지 않는다.** 표현이 바뀌지 품질이
바뀌는 게 아니다.

### 그래서 무엇이 열렸나

6GB 제약을 지킬 이유가 사라졌다. 서버(24GB)로 통일하면

- 모델을 압축하지 않아도 된다 → 압축 손실 **−0.0604**가 사라진다
- 더 큰 모델(8B·14B·32B)이 정상 후보로 복귀한다
- 생성 속도가 **9.5배** 빨라진다
- **재현 가능해진다** — 지금은 "특정 노트북에서만 만들 수 있는 산출물"이라는 약점이 있다

## 5. 지금 남은 결정 하나

**캡션 모델을 바꿀 것인가.** 근거는 거의 다 모였는데, 확인할 게 하나 남았다.

독립 확증에서 비교한 두 조건이 이랬다.

```
현행   Qwen2.5-VL-3B   압축(4bit)     0.4808
후보   Qwen3-VL-4B     비압축(bf16)   0.5150     차이 +0.0342
```

**압축 여부가 다르다.** 6GB 노트북을 전제하던 때는 저게 실제 배포 조건이라 맞는
비교였는데, 서버로 통일하면 현행도 비압축으로 돌게 된다. 그러면 저 +0.0342 중
얼마가 모델 덕분이고 얼마가 비압축 덕분인지 갈리지 않는다.

무시할 수 없는 크기다 — 후보 모델에서 압축 손실이 0.0604로 실측됐기 때문이다.

**해결: 현행 모델도 비압축으로 한 번 돌려 조건을 맞춘다.** 판정 규칙은 결과를 보기
전에 정해뒀다 — 조건을 맞춘 뒤에도 후보가 이기면 모델 교체, 차이가 사라지면 현행 유지.

### 결과 (8/11 오후 추가)

| arm | 캡션 성능 | 융합 성능 |
|---|---|---|
| 현행 Qwen2.5-VL-3B (비압축) | 0.4773 | 0.4741 |
| 후보 Qwen3-VL-4B (비압축) | **0.5150** | 0.4928 |

| 지표 | 차이 | 판정 |
|---|---|---|
| **캡션 성능** (사전에 정한 주 지표) | **+0.0377** | **통과** |
| 융합 성능 | +0.0187 | 오차범위가 0을 걸침 |

**교란이 풀렸다.** 현행 모델은 압축 손실이 사실상 없었고(0.4808 → 0.4773), 조건을
맞추자 차이가 오히려 **커졌다**(+0.0342 → +0.0377). 즉 **모델 교체 근거가 성립한다.**

다만 융합 성능은 오차범위가 0을 걸친다. 이유가 둘 있다.

1. 후보는 **장면 설명 채널만** 바꾸는데 융합은 음성 자막 채널을 절반 섞는다. 개선분이
   희석된다.
2. 융합 비율(α=0.5)이 **현행 모델에 맞춰 튜닝된 값**이다. 후보의 최적값은 0.4이므로
   지금 수치는 후보에게 불리한 하한이다. 비율을 후보에 맞춰 다시 재는 작업이 남았다.

## 6. 별도 안건 — 평가 지표를 채점하던 심판이 부실했다

리포트 생성 모듈(M9)의 평가 지표 중 **coverage(리포트가 내용을 빠뜨리지 않았는가)**를
채점하는 판정자를 검정했다. **정답을 아는 문항**을 만들어 주고 맞히는지 봤다.

| 판정자 | 크기 | coverage 정답률 | 판정 |
|---|---|---|---|
| 현행 (Qwen2.5-7B) | 7B | **0.550** | 탈락 |
| 다른 계열 (kanana) | 8B | **0.417** | 탈락 |
| 같은 계열 더 큰 모델 (Qwen2.5-14B) | 14B | **0.767** | **통과** |

**결론: 지표가 잘못된 게 아니라 심판이 부족했다.** 계열을 바꿔도 안 됐지만 용량을
키우니 통과했다. 즉 **판정자를 14B로 교체하면 지표를 살릴 수 있다.**

다만 두 가지를 같이 봐야 한다.

- 14B는 통과선(0.75)을 **0.767로 겨우 넘겼다.** 문항이 60개뿐이라 여유가 크지 않다.
- 14B만 메모리 때문에 **압축해서 돌렸다.** 압축은 보통 성능에 불리하므로, 불리한
  조건에서도 통과했다는 점은 결론을 약화시키지 않는다.

**영향:** 이미 test 데이터에서 이 지표로 두 번 수치를 냈다. 그 수치들은 부실한
심판이 매긴 점수이므로, **재산출하거나 한계를 명시해야 한다.** 결과가 나쁘게 나온
게 아니라, **그 숫자를 믿을 근거가 없었다**는 뜻이다.

## 7. 튜터께 여쭙고 싶은 것

1. **test 재평가를 열어도 되는가.**
   모델·기계·압축 설정을 바꾸면 최종 평가를 다시 돌려야 한다. 지금까지 test는
   확정된 설정으로 **7회만** 접촉했고 튜닝에는 한 번도 쓰지 않았다.
   변경을 확정하면 8회차가 된다. 재평가 전에 **바꿀 항목·판정 기준을 모두 결과 보기
   전에 고정**할 계획인데, 이 방식이 방어 가능한지 확인받고 싶다.

2. **"최고 성능이 특정 노트북에서만 나온다"를 한계로 쓸 뻔했던 건에 대해.**
   결과적으로 사실이 아니었지만, 작은 표본(96건)의 노이즈를 며칠간 전제로 삼았다.
   앞으로 **어느 정도 표본에서 나온 결과부터 의사결정에 쓸지** 기준을 정하고 싶다.

3. **모델 크기를 어디까지 열 것인가.**
   6GB 제약이 풀려 8B·14B·32B가 후보가 될 수 있다. 다만 모델마다 프롬프트를 다시
   튜닝해야 공정한 비교가 되어 비용이 크다. **이미 독립 확증을 통과한 4B를 채택하고
   마무리할지**, **더 큰 모델까지 확인하고 갈지** 판단이 필요하다.

4. **평가용 판정자를 교체하고 기존 수치를 재산출하는 것**이 맞는지.
   판정자를 14B로 바꾸면 지표를 살릴 수 있음을 확인했다. 다만 이미 test에서 낸
   두 번의 수치는 부실한 심판이 매긴 것이라 그대로 쓸 수 없다. **재산출할지,
   한계 명시로 갈지** 판단이 필요하다.

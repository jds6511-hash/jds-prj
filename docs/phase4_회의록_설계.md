# Phase 4 — 회의록 생성 평가 설계

**상태:** 설계 확정(2026-08-09), 미착수. 서버 GPU 필요(로컬 6GB 불가, M8/M9와 동일 제약).
**선행:** Phase 2(STT 고유명사, 종결) · Phase 3(화자분리, 종결) · Phase 3-b(클러스터 순도, 종결).
근거 수치는 `docs/작업현황_2026-08-04.md` §Phase 3 / 3-b.

---

## 1. 범위 — 회의록만 한다. 화자별 요약은 제외한다

**결정(2026-08-09): 화자별 요약을 범위에서 뺀다.** 이건 일정 문제가 아니라 **측정
가능성 문제**다.

화자별 요약은 "이 사람이 무슨 말을 했는가"를 주장한다. 그 주장의 정확도는 **구간
배정 정확도(DER)** 에 직접 의존하는데, **DER은 측정하지 못했고 앞으로도 못 한다** —
공식 회의록에 타임스탬프가 없어 프레임 단위 정답을 만들 수 없다(3-b 서두). 대신 잰
클러스터 순도 0.9583은 표본이 **앵커 24건, 안건 보고자 편중**이라 모든 화자로
일반화되지 않는다(앵커 수율: 타깃 389건 → 34건, A2 6자 미만에서 160건 탈락).

즉 화자별 요약을 만들면 **정확도를 뒷받침할 지표 없이 인물별 발언을 단정**하게 된다.
회의 도메인에서 그건 단순한 성능 미달이 아니라 오귀속이다. 만들지 않는 것이 맞다.

회의록은 다르다. 회의록은 **"이 회의에서 무엇이 논의됐는가"** 를 주장하며, 화자
라벨은 서술을 조직하는 보조 정보로만 쓴다. 화자 배정이 틀려도 안건 내용의 정확도는
독립적으로 채점할 수 있다. **측정 가능한 것만 주장한다.**

*이 제외는 되돌릴 수 있다 — 타임스탬프 라벨링을 해서 DER을 재면 그때 다시 올린다.
그 전에는 아니다.*

## 2. 파이프라인

기존 모듈을 재사용한다. 새로 만드는 것은 프롬프트와 채점기뿐이다.

```
회의 오디오(wav)
  ├─ m3_generate.transcribe        운영 코드 직접 호출(인자 복사 금지 — Phase 2 사고)
  │    → 발화 단위 전사 + 타임스탬프
  └─ meeting_diarize (pyannote)    → 화자 턴(시작·끝·클러스터)
         │
         ▼
   화자 귀속 전사문   턴과 발화를 시간 겹침으로 결합
         │           겹침이 갈리면 최대 겹침 턴에 붙이고 `split=true` 기록
         ▼
   M8식 map-reduce 생성            llm_4bit: false, 7B bf16 (서버 20.1GB 실측)
         │                        report_max_new_tokens 16384 (M8 결함 ② 대응)
         ▼
   회의록 초안 (인용 마커 포함)
         │
         ▼
   M9식 이중 평가                  아래 §3
```

**M8의 결함 4건은 이미 고쳐진 경로를 그대로 탄다** — 서술 빔·생성 상한 절단·번호
몰아쓰기·반복 루프(DESIGN_SPEC 8-5(6-a)~(6-f)). 회의는 브이로그보다 발화 밀도가
높아 ③ 번호 몰아쓰기가 재발할 소지가 크므로, **감지 시 상향** 규칙의 발동 여부를
회의별로 기록한다. 규칙을 기본 경로에 넣지 마라(정상 입력이 깎인 전례: 커버
0.844→0.418).

**입력 길이.** c20이 165분이다. M8 map-reduce가 그대로 필요하다 — 단일 프롬프트로
넣지 않는다. 청크 경계는 **화자 턴 경계에 맞춘다**(문장 중간 절단이 귀속을 깨뜨린다).

## 3. 평가 — 세 축을 따로 잰다

공식 회의록을 정답으로 쓰되, **그것이 무엇을 보증하고 무엇을 보증하지 않는지**를
축마다 명시한다. 공식 회의록은 개조식 요약이라 **누가 그 말을 실제로 발음했는지
보증하지 않는다**(3-b에서 불일치 3건이 전부 이 이유였다).

| 축 | 무엇을 잰다 | 정답 | 한계 |
|---|---|---|---|
| **A. 안건 커버리지** | 공식 회의록의 안건 항목이 생성 회의록에 나타나는가 | 공식 회의록 안건 목록 | 안건 단위라 조밀하지 않다 |
| **B. 근거성(grounding)** | 생성 문장이 전사문의 실제 발화에 붙어 있는가 | 전사문 자체 | 전사 오류는 통과시킨다 |
| **C. 고유명사 환각** | 생성 회의록의 고유명사가 전사문에 있는가 | 전사문 자체 | Phase 2 인프라 재사용 |

**A는 M9의 coverage, B는 M9의 grounding과 같은 계약**이다. 새 판정기를 만들지 않고
M9 판정기를 회의 입력으로 돌린다 — 지표 정의가 바뀌면 M8/M9 결과와 비교가 끊긴다.

**C가 이 도메인 고유 축이다.** Phase 2에서 고유명사 타깃 389건이 이미 동결돼 있고
발화 검증까지 끝나 있다. 생성 회의록에서 고유명사를 뽑아 전사문에 **정확히 존재하는지**
확인한다(근사 매칭 금지 — 거리 0만, 3-b 필터 A3과 동일 규칙). 없으면 환각이다.
인명·기관명을 지어내는 것이 회의록에서 가장 치명적인 실패 양식이다.

### 사전 등록 — 실행 전에 못박는다

- **표본은 회의 3편 전량**(c26 42분 / c13 127분 / c20 165분, 합 334분). 결과를 보고
  회의를 빼지 않는다.
- **프롬프트 튜닝은 c26 1편에서만** 한다. c13·c20은 확정 프롬프트로 1회만 돌린다.
  M8에서 프롬프트를 결과 보고 고친 전례가 있어, 여기서는 튜닝 대상을 먼저 격리한다.
- **화자 라벨은 클러스터 ID로만 표기**한다(`SPEAKER_09` 등). 실명 매핑을 하지 않는다 —
  매핑의 정확도가 미측정(DER 부재)이기 때문이다. §1과 같은 이유다.
- 지배 클러스터(발화 35~43%)는 사회자로 **추정**되지만 그렇게 라벨하지 않는다.

## 4. 이 평가가 답하지 못하는 것 (발표에서 물으면 그대로 말한다)

1. **DER 미측정.** 어느 구간이 누구인지의 정확도는 모른다. 클러스터 순도는 대체물이
   아니며 표본도 편중돼 있다.
2. **프록시 도메인.** 이 프로젝트의 대상 코퍼스는 국무회의가 아니라 브이로그 7편이다.
   회의를 쓴 이유는 공식 회의록이 정답을 공짜로 주기 때문이고, 브이로그로 재검증하려면
   축자 정답을 새로 써야 한다. Phase 2에서 이미 인정한 한계이며 감추지 않는다.
3. **전사 오류는 B·C를 통과한다.** 두 축의 정답이 전사문이라, 전사가 틀린 채로
   회의록이 그것을 충실히 옮기면 만점이 나온다. 이건 설계상 의도된 분리다 —
   전사 품질은 Phase 2에서 따로 쟀다.
4. **회의록 인용·복창.** 사회자가 안건을 읽으면 회의록 귀속자와 실제 발화자가 다르다.
   A축은 안건 단위라 영향이 없지만, 화자 라벨을 붙이는 어떤 주장도 이 함정을 밟는다.

## 5. 실행 전 점검

- [ ] 서버 GPU 예약(캘린더, `[<LAB_MACHINE>-GPU] …`). `config_server.yaml` 사본 사용 —
      본 `config.yaml` 편집 금지.
- [ ] `HF_HOME=/ssd/$USER/cache` 명령마다 명시(비대화형 SSH는 `.bashrc`를 안 읽는다).
- [ ] `torchcodec` 미설치 유지. pyannote는 `{"waveform": …, "sample_rate": …}` 직접 전달로 동작한다.
- [ ] `data/meeting_probe/` STT 캐시 주의 — 회의 3편이 한 디렉터리라 `stt_cache.json`이
      서로 덮어쓴다. 3편 전사는 매번 처음부터(~22분). 운영은 영상당 디렉터리가 갈리므로
      정상이며 고치지 않는다.
- [ ] 프롬프트 튜닝을 c26으로 끝낸 뒤에만 c13·c20을 돌린다.

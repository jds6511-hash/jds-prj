## 감사 방법

각 ID를 이 다섯 칸으로 채우지 못하면 UNPROVEN이다.

```
matrix requirement  →  concrete test  →  actual perturbation  →  compared projection  →  assertion
```

비교 projection은 시간 구조로 한정한다(OPEN-4).

```
넣는다      boundary_positions · spans · episode_id · start_seg · end_seg
           start_sec · end_sec · 순서 · 개수
넣지 않는다   content · raw bytes · hash · run_id · 판정
근거        OPEN-4 CLOSED — DET-002는 **byte equality를 요구하지 않는다.**
           run_id·시각이 문서에 들어가므로 byte equality는 애초에 성립하지 않는다.
```

## PROVEN 2 (감사 시점)

### DET-001 — same video + config → canonical partition 동일  (P0) **PROVEN**

```
matrix   same video + config → canonical partition 동일
```

증거.

```
test_fw_001_identical_input_gives_identical_partition
    같은 segment 격자 · 같은 config로 **5회** 실행 → boundary_positions 전부 동일
test_aar_006_structure_is_identical_across_runs
    독립적인 두 파이프라인 실행(run-001 · run-777) → structural_signature 동일
test_builder_output_passes_the_independent_validator
    S1·S2·S3에서 window_spans 출력이 독립 validator(A-09)를 통과한다
test_episodes_build_from_the_fixed_window_partition
    window_spans → build_episodes 합성 경로가 실제로 이어진다
```

두 층이 나뉘어 있다는 점을 적어 둔다 — 첫 테스트는 **partition 파생**의 결정성이고,
둘째는 **정본 문서 구조**의 결정성이다. 둘의 합집합이 DET-001 요구를 덮는다. 하나로는
덮지 못한다.

구조적 사실 하나. **production에는 `segments → window_spans → build_episodes → aar`를
한 번에 도는 orchestrator가 없다.** `v2_1_run`은 run layout·manifest만 담당한다. 그래서
end-to-end 결정성 증거는 테스트 쪽에서 조립해야 하고, E-02 증거 테스트가 그렇게 한다.

### DET-006 — serialization rerun → ids/ordering 안정  (P1) **PROVEN**

```
matrix   serialization rerun → ids/ordering 안정
```

증거.

```
test_aar_007_roundtrip_preserves_meaning       load(serialize(doc)) == doc
                                              dict 동일성이 episode 목록 순서·id를 포함한다
test_lineage_survives_a_roundtrip              load_lineage(serialize_lineage(x)) == x
test_aar_007_serialization_is_deterministic    serialize(doc) == serialize(doc)
```

`byte equality`를 요구하지 않았다. 왕복 동일성 + 직렬화 결정성의 조합이
`serialize → deserialize → serialize`에서 id·순서 유지를 함의한다.

다만 **독립 재생성 후 직렬화**(같은 입력으로 세 번 다시 만들고 id·순서를 비교)는
없었으므로 E-02에서 한 건 보강했다.

## UNPROVEN 5 (감사 시점) — 전부 evidence-gap

### DET-002 — rerun N≥3 → boundary list + episode 구조 동일  (P0)  **UNPROVEN**

```
matrix   rerun N≥3 → boundary list·episode 구조 동일 (§OPEN-4)
```

있던 것.

```
test_fw_001_identical_input_gives_identical_partition   N=5 이지만 boundary_positions만 본다
test_fw_010_long_input_is_deterministic                 N=2
test_aar_006_structure_is_identical_across_runs         episode 구조는 보지만 N=2,
                                                       그리고 spans가 하드코딩된 입력이다
```

없던 것.

```
**N≥3**에서 boundary 목록과 episode 구조를 **함께** 비교한 테스트
= "N≥3 + 두 projection 동시"
```

분류: **evidence-gap.** 두 요구가 서로 다른 테스트에 흩어져 있었고, N≥3을 만족하는
쪽은 projection이 하나뿐이었다. DET-001과 합치면 안 되는 이유가 여기다 — DET-001은
입력 결정성이고 DET-002는 **반복 횟수와 두 projection**을 명시한 별도 계약이다.

### DET-003 — different LLM → canonical partition 동일  (P0)  **UNPROVEN**

```
matrix   different LLM → canonical partition 동일
```

있던 것.


```
REPEATS = 5   (matrix N≥3)
경로   격자 → window_spans → build_episodes → provider boundary
비교   boundary_positions · spans · episode(id·start_seg·end_seg·start_sec·end_sec) · 개수
```

## DET-007 — parallel execution

```
실행      ThreadPoolExecutor 8 worker. run layout(create_run)까지 실제로 만든다
핵심 설계  **worker마다 다른 입력을 준다** — (S1,20) (S2,60) (S1,60) (S3,20)
                                        (S2,20) (S4,60) (S5,20) (S1,15)
         전부 같은 입력으로 돌리면 thread 사이로 상태가 새어도 결과가 우연히 맞는다
비교      각 worker의 결과를 **자기 직렬 baseline과** 대조한다
부수 확인  입력이 실제로 갈렸는지(서로 다른 spans가 2종 이상) · run 디렉터리 8개 분리
2번째 arm  provider registry를 공유한 32회 동시 조회 → 결과 1종
```

isolation 근거를 적어 둔다. `RawStore`는 같은 run 안에서 덮어쓰기를 거부하고
(`RAW-006`), 비충돌은 **raw_root가 다를 때만** 보장한다. run 분리는 `create_run`의
layout(`root/video_id/run_id/`)이 담당하며 기존 run 위에 덮어쓰지 않는다. DET-007은
그 layout 아래에서 측정했다 — 같은 root를 공유하며 run_id만 다른 8개 run이다.

```
byte equality는 요구하지 않는다
```

## mutation 6건

```
1  window_spans가 3회마다 경계 하나를 옮긴다            DET-002 RED
2  content_status가 end_seg에 섞인다                   DET-003 RED
3  caption 텍스트 길이가 episode start_sec에 섞인다      DET-004 RED (3 arm)
4  OCR 텍스트 길이가 episode start_sec에 섞인다          DET-005 RED (3 arm)
5  정본 조립 때 episode_id를 전역 counter로 재번호       DET-006 RED
6  build_episodes가 입력을 module-level dict에 얹는다    DET-007 RED
```

6번이 이 감사의 핵심이다.

```
같은 주입에서   DET-007  RED     (thread 간 누출이 결과에 드러난다)
              DET-002  GREEN   (직렬 반복에서는 자기 입력만 보므로 정상이다)
```

즉 **DET-007은 직렬 결정성 테스트가 원리적으로 잡을 수 없는 결함을 잡는다.** 이것이
`parallel execution` 계약을 별도로 두는 이유이고, 구조 추론으로 대체할 수 없는 이유다.

3번·4번의 첫 시도는 "채널이 있는가/없는가"에만 반응하게 만들었더니 EMPTY arm만 RED였다.
**내용 길이**에 반응하도록 고쳐 3 arm 전부 RED가 됐다 — 주입이 약하면 테스트의 강도를
잘못 판정한다.

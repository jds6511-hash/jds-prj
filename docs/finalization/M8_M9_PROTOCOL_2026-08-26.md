# M8 → M9 → 최종 문서: 완료 프로토콜 (2026-08-26)

프로젝트 종료선을 다시 정의한다.

```
M1~M7  검색 시스템                    완료
M8     근거 추적 가능한 AAR 생성 + dev에서 생성 방식·평가 규칙 확정 → freeze
M9     동결된 M8을 공식 test에서 검증                    (test-opening 승인 사건)
POST   검증된 report.json → HWPX/HWP 렌더                (LLM 호출 없음)
```

**M8/M9는 더 이상 future work가 아니다.** 단 공식 test 개방은 여전히 비가역 승인 사건이다.

`report.json`이 canonical AAR이고, `report_eval_*.json`이 검증 결과이며, HWP/HWPX는
그 둘이 확정된 뒤의 표현 계층이다.

## 1. 기존 설계 복구 (추측 없음 — 전부 소스 인용)

### A. M8의 원래 목적

> DESIGN_SPEC 4-8: 입력 `segments.json` → 출력 `report.json`. `[seg#N]` 인용 강제,
> map-reduce(n_segments > chunk_size), `parse_citations`로 문장별 인용 추출,
> `raw_output` 항상 보존.

즉 **근거(seg 인용)가 붙은 문장 집합**을 만드는 것이 M8이다. 요약문 품질 점수가 아니다.

### C. 원래 M8 COMPLETE 조건 — 이미 동결돼 있다

`docs/preregistration/M8_구조변경_사전등록_2026-08-16.md` §2-3:

```
C1  Catastrophic failure 0편          (다른 언어 이탈 · 조기 종료 · 반복 루프)
C2  Event Recall 중앙값 ≥ 0.70        (주 지표. 평균이 아니라 중앙값)
C3  Compression ≤ 2.0                (정답 사건 하나를 두 문장 넘게 쓰지 않는다)
```

표본 요구(§3): **구조 선택 판정은 8~12편.** "3편으로는 판정하지 않는다."

§4 미결 사항이 그대로 남아 있다:

> Event Recall 판정을 사람이 할지 judge 모델이 할지 아직 안 정했다. judge를 쓰면
> **judge 자체를 먼저 검증**해야 한다 — M9에서 판정자가 고장나 있던 전례가 있다.

### D. 미완 항목

```
① Event Recall 판정 주체 미결정        사람 / judge(검증 선행) — C2 집행의 전제
② reference 사건 목록 2편(53건)뿐      C2 판정에는 8~12편 필요
③ 관문 C1~C3 미집행                   pilot은 "판정 아님"으로 명시된 관측 실행이었다
④ M9 acceptance threshold 부재         저장소 전체에서 M9 PASS 기준을 찾지 못했다
⑤ human review 규칙                   `human_check_n: 20` 스팟체크만 존재(동일모델 judge 보정용)
```

**실패 유형 taxonomy는 이미 동결돼 있다** — 새로 만들 것이 아니다.
`docs/재분석_M8pilot_2026-08-18.md` §3:

```
overmerge · boundary_too_wide · boundary_shift · missed_event · spurious_event · reasonable_match
```

같은 문서가 "M8 research evaluation(6분류 taxonomy·human review)"으로 부르는 것이 이것이다
(`AAR_TRACEABILITY_2026-08-25.md`). 따라서 이번 제안의 9종 error taxonomy는 **신규 도입이
아니라 기존 6분류와의 관계를 정해야 하는 사안**이다.

### D-1. 표본 소비 제약 — 이것이 가장 강한 제약이다

`docs/재분석_M8pilot_2026-08-18.md` §3:

> **표본은 소비됐다.** `gwaktube`·`kheritage`는 이후 metric·threshold·event-unit 규칙
> 변경의 확증 표본으로 재사용하지 않는다. semantic rubric을 새로 만들 경우 이 두
> 영상에서 확증하지 않는다.

즉 **reference 사건 목록이 있는 유일한 2편을 C2 판정에 쓸 수 없다.** 8~12편 판정 표본은
**다른 영상**에서 새로 만들어야 한다. dev 3편 중 남은 것은 `_10_000…` 1편이고 그것도
`reference_status = not_applicable`(사건 수가 로그에 노출돼 독립 reference 불가)이다.

따라서 C2 집행에는 **신규 영상 확보 + 사람 사건 라벨링**이 선행한다. 이것은 이번 작업
범위 밖이고 별도 승인 사건이다.

pilot 실측(2편·reference 53건, `docs/재분석_M8pilot_2026-08-18.md`):

```
event_temporal_alignment          0.1642
temporal_event_recall@IoU>=0.3    0.3019      ← C2 기준 0.70과 큰 격차
@0.5 / @0.7                       0.1509 / 0.0377
timeline_span_coverage            0.87~0.96 (진단값)
```

**이 수치는 판정이 아니다**(영상 2편·CI 없음). 다만 C2를 그대로 집행하면 현 구조가
통과하지 못할 가능성이 높다는 사실은 지금 알고 있어야 한다 — 그리고 **결과를 보고
기준을 낮추는 것은 금지**다(같은 문서 §0이 1차 판정 실패를 그대로 남긴 이유).

### E. M9의 원래 목적

> DESIGN_SPEC 4-9: 입력 `report.json` + `segments.json` + `queries.jsonl(test)` +
> judge LLM → 출력 `report_eval_<video_id>.json`.
> `coverage_rate`(리포트가 gt 세그먼트 내용을 언급했는가) ·
> `groundedness_rate`(인용 세그먼트가 문장을 뒷받침하는가, 단방향 entailment) ·
> `coverage_by_type`(자막형/장면형/복합형).

### F. M9의 평가 단위 — 둘이다

```
groundedness   리포트 **문장**당 1건 (cites==[] 문장은 judge 호출 없이 ungrounded)
coverage       **gt 세그먼트**당 1건 (test 질의의 gt_seg_idx 합집합)
```

**질의 39건이 평가 단위가 아니다.** 질의는 gt 세그먼트를 정의하는 데만 쓰인다.

### G. test39와의 관계

`m9_report_eval.main`이 `split=="test"`인 질의를 video_id로 걸러 `gt_seg_idx`를 모으고,
그 세그먼트가 coverage 판정 대상이 된다. `--test-opening` 사유 없이는 실행되지 않는다
(2026-08-26 감사에서 추가). 즉 M9는 test 4편 각각에 대해 리포트를 1개씩 만들어 평가한다.

## 2. 제안 ↔ 기존 설계 충돌

| 항목 | 기존 설계 | 이번 제안 | 충돌 | 권고 |
|---|---|---|---|---|
| report 구조 | `sentences[{sent_id,text,cites}]` + 선택적 `events[]` (schema v2) | `summary/events/observations/limitations` + `claim_id` | 이름만 다름, 기능 동등 | **기존 유지.** 스키마 변경은 validator·테스트 136건·기존 산출물을 무효화한다. 렌더 계층에서 4덩어리로 배치하면 된다 |
| 평가 방식 | judge LLM 이진 판정(coverage/groundedness) + 사람 스팟체크 20 | 사람 claim 단위 4축 rubric | **충돌** | judge 판정을 사람 rubric으로 **대체**하려면 outcome-blind amendment + 승인. 대안: 기존 judge 지표를 주로 두고 사람 4축을 **표본 검증**으로 병기 |
| 주 지표 | M8 = Event Recall 중앙값 / M9 = coverage·groundedness | claim support 분포 · unsupported rate | 부분 충돌 | M8 관문은 그대로. claim 4축은 **M9 사람 검증 표본**의 라벨 체계로 도입 가능(신규 지표를 주 관문으로 올리지 않는다) |

| 인용 없는 문장 | `aar_view` **거부** / M9 **자동 ungrounded** | — | **기존 내부 불일치** | test 개방 전에 하나로 정해야 한다(§3-B) |
| composite 점수 | 없음 | 만들지 않음 | 일치 | 유지 |

**D2가 실질적 병목이다.** C2(Event Recall 중앙값 ≥ 0.70)를 동결된 그대로 집행하려면
사람이 8~12편의 사건 목록을 새로 만들어야 한다. 대안 경로는 셋이고 **전부 승인 사항**이다.

```

        가장 원설계에 충실. 사람 작업량이 가장 크다
경로 B  C2를 집행하지 않고 **관문 미집행 상태를 그대로 명시**한 뒤 M8을 freeze,
        M9는 coverage·groundedness만으로 검증
        보고서에 "구조 선택 판정은 표본 부족으로 미집행"을 한계로 적는다
경로 C  판정 범위를 문장 근거성(M9 지표)으로 좁히고 사건 정렬은 진단으로만 보고
        Event Recall을 주 관문에서 내리는 것이므로 outcome-blind amendment 필요
```

**아래 권고는 2026-08-26에 기각됐다** — 경로 A로 확정. 사유는
[M8_M9_DECISIONS_2026-08-26](M8_M9_DECISIONS_2026-08-26.md) §D2에 있다. 기록으로 남긴다.

권고는 **경로 B**다. 이유: ① C2는 "구조 선택"(문장형 vs 사건형) 판정용 관문이고 배포
파이프라인은 이미 문장형으로 산출물을 냈다 ② 표본 소비 선언 때문에 지금 있는 reference로는
어떤 판정도 확증이 되지 않는다 ③ 미집행을 미집행이라고 적는 것이 기준을 낮추는 것보다
방법론적으로 안전하다. **다만 이것은 방법론 결정이므로 사용자 승인 사항이다.**

**D1~D5가 정해지기 전에는 M8 freeze를 할 수 없고, freeze 없이는 M9를 열 수 없다.**

## 4. M9 acceptance threshold — 후보 (승인 필요, 임의 확정 금지)

기존 설계에 M9 PASS 기준이 없다. 아래는 **제안**이며 사용자 승인 후 동결한다.

### 구조 검증 (자동, 사람 판정 전)

| 항목 | 제안 | 근거 |
|---|---|---|
| 구조 validator | **100% PASS 요구** | 이미 fail-closed로 구현돼 있다(`aar_view`). 하나라도 깨지면 그 리포트는 추적 불가이므로 내용 평가가 무의미하다 |

### 내용 검증

| 지표 | 후보 A (보수) | 후보 B (완화) | 비고 |
|---|---|---|---|
| `groundedness_rate` | ≥ 0.80 | ≥ 0.70 | dev 실측이 없다 — pilot은 event 지표만 산출했다. **근거 없이 고르면 안 된다** |
| `coverage_rate` | ≥ 0.60 | ≥ 0.50 | test 4편의 gt 세그먼트 수는 39질의 gt의 합집합이다 |
| `coverage_by_type` | 최저 유형 ≥ 0.40 | 보고만 | 유형별 약점을 감추지 않기 위한 항목 |
| unsupported 문장 비율 | ≤ 0.20 | 보고만 | `1 - groundedness_rate`와 중복이라 별도 관문으로 두지 않아도 된다 |

**권고 순서:** ① dev 3편에서 M9 함수를 dev 질의로 돌려 groundedness 분포를 먼저 본다
(dev는 열려 있다) → ② 그 분포를 근거로 threshold 확정 → ③ 동결 → ④ test 개방 요청.

이 순서를 지키면 "기준을 결과에 맞춰 정했다"는 지적을 받지 않는다. **dev로 threshold를
정하는 것은 허용되고, test로 정하는 것은 금지다.**

## 6. M9 실행 규율 (개방 승인 후)


결과를 본 뒤 금지: 프롬프트·스키마·taxonomy·threshold·판정 규칙 변경, 실패 문장을 보고
규칙 추가. 허용: **결과를 보지 않은 상태의 인프라 장애**(크래시·OOM·전송 손상)에 대한
동일 config 재시도. 구조 validator 실패는 수동 패치하지 않는다.

**M9 COMPLETE ≠ M9 PASS.** 프로토콜을 끝까지 수행하고 결과를 동결·보고하면 COMPLETE다.
FAIL이어도 숨기지 않고 그대로 적는다.

## 7. POST-M9 문서 산출

```
report.json + report_eval_*.json → 결정적 렌더러 → report.hwpx → (필요 시) report.hwp
```

렌더러 규칙: **새 LLM 호출 없음 · 새 요약 생성 없음 · claim/인용 수정 없음.** 서식만.
구조는 `docs/finalization/AAR_SAMPLE_*.md`(현행 마크다운 렌더)의 순서를 그대로 쓴다 —
표지 · 대상·provenance · 전체 요약 · 사건 타임라인 · 핵심 관찰 · claim별 시각·인용 ·
상세 증거 · 한계 · **M9 검증 상태** · 생성 정보.

M9가 FAIL이거나 미실행이면 "검증됨"이라고 쓰지 않는다. verdict를 그대로 표시한다.

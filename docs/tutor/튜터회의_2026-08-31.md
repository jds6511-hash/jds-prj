## 00. 회의에서 말할 내용 (한 페이지)

**이번 주에 한 일은 크게 셋입니다.**

**① 자동 보고서 생성(M8)을 공식 평가했고, 떨어졌습니다.** 8편·68개 사건을 사람이
직접 라벨링해 정답을 동결한 뒤 평가했더니 관문 3개 중 3개 모두 미달이었습니다.
개선안을 두 번 돌렸지만 **원래 멀쩡하던 영상을 망가뜨리는 회귀**가 나와서 3라운드는
하지 않고 종결했습니다. **이 FAIL 판정은 소급해서 바꾸지 않습니다.**

**② 왜 실패했는지를 진단했고, 원인이 "모델이 나빠서"가 아니었습니다.** 큰 모델
(Kanana-8B)로 바꿔 같은 조건에서 재보니, **모델을 바꿔도 같은 붕괴가 나고 조건을
바꾸면 어느 모델이든 붕괴**했습니다. 즉 문제는 모델 선택이 아니라 **LLM에게 시간
경계를 자유롭게 정하게 한 설계**였습니다.

**③ 그래서 설계를 바꿔 v2.1을 새로 만들고 있습니다.** 핵심은 **"기계가 관리하는
정본"과 "사람이 읽는 표현"을 분리**하는 것입니다. 경계는 코드가 정하고, LLM은 그
안에서 내용만 씁니다. 근거 없는 문장은 검증기가 걸러냅니다.
**Gate A(정본 골격)와 Gate B(내용·근거)는 끝났고, Gate C(표현)를 진행 중입니다.**

**상의하고 싶은 것 세 가지.**
① M8 FAIL을 결과 없는 실패가 아니라 **설계 결함을 특정한 진단 결과**로 보고해도 되는지,
② 남은 기간을 v2.1 완성(문서 생성까지)에 쓰는 방향이 맞는지,
③ 표현 계층의 문장 생성을 지금처럼 **LLM 없이 결정적 조합**으로 두는 게 맞는지.

검색 파이프라인은 이미 동결돼 있다. **이번 주는 전부 뒤쪽(보고서)에서 일어난 일이다.**

## 3. 실패 원인 진단 — 모델이 아니라 설계 (08-29~08-30)

### 3-1. 물어본 것

> **후보 모델이 진 것인가, 파이프라인이 이득을 죽인 것인가?**

이 프로젝트의 규율이다. "비유의"를 "차이 없음"으로 쓰지 않는다.

### 3-2. 같은 조건에서 다른 모델로 재봤다

```
현재 모델   Qwen2.5-7B-Instruct       저장된 출력 재사용
비교 모델   Kanana-1.5-8B-Instruct    신규 4호출 · 패치 0 · 사전등록 후 실행
EXAONE-3.5  IMPLEMENTATION_BLOCKED (라이브러리 비호환) · 과학적 결과 없음으로 종결
출처  docs/finalization/MODEL_DEGENERACY_DIAG_RESULT_2026-08-30.md
```

관찰된 붕괴 형태는 **경계 번호를 등차수열처럼 쭉 늘어놓는 것**(`2,4,6,8…`)이었다.

```
arm                       최장 연속정수   등차열
Qwen   caption  chunk3          1          2칸@59      정상
Kanana caption  chunk3         52          3칸@2       붕괴  ←
Qwen   full     chunk5         26         16칸@2       붕괴  ←
Kanana caption  chunk5         23          2칸@2       붕괴  ←
```

**결론: 조건을 바꾸면 어느 모델이든 붕괴한다.** 모델 교체로 해결되는 문제가 아니다.
따라서 **추가 모델 비교를 중단**했다.

### 3-3. 그래서 무엇이 문제였나

**LLM에게 "어디서 장면이 바뀌는지 직접 골라라"라고 시킨 것**이 문제였다. 자유형
경계 선택은 모델·입력 채널에 따라 경계 위치와 조각 수가 크게 흔들렸고, 정상으로
보이는 출력에서도 의미 기반 경계 대신 **균등 간격·번호 열거 패턴**이 반복됐다.

보조 관찰로, 캡션 임베딩 거리의 peak로 경계를 잡을 수 있는지도 봤지만
`MIXED_SIGNAL`이었다(`C0_BOUNDARY_SIGNAL_OBSERVATION_2026-08-30.md`).
**관찰만 하고 채택하지 않았다** — threshold를 맞추기 시작하면 그게 곧 튜닝이다.

## 4. v2.1 재설계 — 정본과 표현의 분리 (08-30~08-31)

### 4-1. 바뀐 원칙 하나

```
v2.0   LLM이 경계도 정하고 내용도 쓴다        → 붕괴가 문서 전체를 오염시킨다
v2.1   경계는 코드가 정한다 (고정 60초 창)
       LLM은 그 안에서 내용만 쓴다
       근거 없는 문장은 검증기가 지운다
       정본(기계) ↔ 표현(사람) 을 분리한다
```

### 4-2. 진행 상태

```
Gate A  정본 골격      COMPLETE   티켓 11/11 · P0 51/51 · P1 12/12
Gate B  내용·근거      COMPLETE   P0 22/22 · P1 6 PASS + 1 WAIVED
Gate C  표현           진행 중     C-01 ~ C-04 완료 / C-05 ~ C-10 남음
Gate D  연구 경계 가드  유지

구현 규모   모듈 21개 · 테스트 파일 28개 · 테스트 함수 615개
전체 스위트  3,294 passed / 1 skipped
```

### 4-3. Gate A — 정본이 갖춰야 할 것

```
A-01  구간 스키마 · 단일 ingest 어댑터        A-07  경계 provider 레지스트리
A-02  실행 레이아웃 · manifest               A-08  fixed_window_v1 (60초)
A-03  raw 저장이 parse보다 먼저               A-09  정본 partition 검증기
A-04  표기는 받고 존재는 지어내지 않는다        A-10  합성 fixture S1~S8
A-05  오염 판정 · 근거 자격                   A-11  연구 경계 가드
A-06  근거 timeline
```

**A-08(만드는 쪽)과 A-09(검사하는 쪽)가 같은 helper를 공유하지 않게 했다.** 공유하면
같은 버그가 양쪽을 동시에 통과한다.

### 4-4. Gate B — 내용과 근거

```
B-01  Episode 구조            B-06  grounding 검증기
B-03  프롬프트 + 계약 해시     B-07  정본 문서 스키마 · 직렬화
B-04  content 병합 · 실패 격리  B-08  실패 주입 9종
B-05  근거 바인딩 (사실만)     B-09  집계
B-02a 어댑터(로컬·결정적)      B-02b 실제 모델 1회 통합
```

핵심은 **"사실 기록"과 "판정"을 다른 층에 둔 것**이다. B-05는 인용이 어디로
해석됐는지를 기록만 하고, 판정은 B-06 하나가 한다. 그래야 어디서 걸렸는지가 남는다.

### 4-5. 실제 모델로 한 번 돌렸다 (랩실 GPU · Qwen2.5-7B)

여기서 **실제 결함 2건**이 나왔고, 둘 다 다르게 처리했다.

```
결함 1   모델이 완전한 JSON을 ```json 코드펜스로 감쌌다
처리     표기(notation)이지 계약 위반이 아니다 → 파서를 고쳤다
         (프롬프트는 건드리지 않았다)

결함 2   프롬프트 예시의 자리표시자 "선택"을 모델이 그대로 베껴 왔다  → OPEN-10
처리     예시를 지우고 "없으면 키를 넣지 않는다"로 바꿨다 → 재실행에서 사라짐
```

두 번째가 중요했던 이유: `"선택"`은 숫자·인용부호가 없어서 **검증기를 그냥
통과했을** 문자열이다. 즉 근거 없는 문장이 정본에 남을 수 있었다.

### 4-6. 남은 결함을 숨기지 않았다 — OPEN-11

수정 후 재실행에서 **같은 부류가 다른 모양으로** 나타났다.

```
dialogue_note에 인용 목록이 들어옴          "[0, 1, 2, …]"
자막이 아예 없는 영상에서 인용 12개를 지어냄
```

다만 이번에는 **검증기가 세 경로 모두 잡아냈다**(dialogue 삭제·요약은 유지).
그래서 Gate B는 닫되, 원인은 `OPEN-11`로 등록해 두고 **표현 계층이 검증 전 데이터를
읽지 못하게 하는 것**을 Gate C의 필수 조건으로 걸었다.

```
Gate B closure   COMPLETE  (판정을 두 번 기록 — BLOCKED였던 이력도 지우지 않았다)
OPEN-11          OPEN · NON-BLOCKING
```

### 4-7. Gate C — 지금 하는 것

```
C-01  표현 입구 계약     COMPLETE   정본 하나만 받는다 · 상류 모듈 import 차단
C-02  Highlight 조합     COMPLETE   중첩 허용 · 정본 불변 · 개수 강제 없음
C-03  출처(lineage)      COMPLETE   어느 구간에서 왔는지 · 표현 바꿔도 불변
C-04  전체 종합          COMPLETE   LLM 없이 결정적 조합 · 한계 명시
C-05 ~ C-10             남음        스키마 · Markdown/HWPX 렌더러 · 실패 정책 · 집계
```

**C-04에서 LLM을 다시 쓰지 않기로 한 것**이 이번 주 마지막 판단이다. 표현 단계에서
생성을 다시 열면 Gate B에서 만든 근거 경계가 무의미해진다.

## 5. 검증 방식에 대해 (질문 나올 만한 것)

테스트가 통과하는 것만으로는 부족하다고 보고, **금지한 변화를 실제로 주입해서
테스트가 깨지는지**를 매 티켓마다 확인했다.

```
예) grounding 검증을 지운다            → 테스트 RED   (가드가 살아 있음)
    실패한 구간을 종합에 포함시킨다      → RED
    highlight 개수에 9개 상한을 넣는다   → RED
    출처를 시간 범위에서 역추론하게 한다  → RED
```

이 과정에서 **가드가 실제로는 아무것도 막지 못하던 경우 3건**을 찾아 고쳤다. 그중
2건은 코드가 아니라 **테스트가 느슨했던 것**이라 테스트를 좁혔다.

## 7. 상의하고 싶은 것

**① M8 FAIL의 보고 방식.**
관문 3개 전부 미달이지만, 그 뒤에 **원인을 모델이 아니라 설계로 특정**했고 대안
설계를 구현 중이다. 이것을 "실패"로 쓸지 **"설계 결함을 분리해 낸 진단 결과"**로 쓸지.

**② 남은 기간 배분.**
지금 v2.1은 Gate C 중반이다. 실제 문서(Markdown/HWPX)까지 생성해 보여주는 데까지
갈지, 아니면 Gate C를 계약 수준에서 닫고 보고서 서술에 시간을 쓸지.

**③ 표현 문장의 품질.**
현재 종합문은 LLM 없이 결정적으로 조합해서 문장이 다소 기계적이다.
읽는 맛을 위해 LLM을 다시 넣으면 근거 검증을 표현 단계에서 또 해야 한다.
지금 상태로 두는 게 맞는지.

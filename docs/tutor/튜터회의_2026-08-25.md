## 00. 회의에서 말할 내용 (한 페이지)

**프로젝트는 긴 한국어 영상에서 자연어 질문으로 원하는 순간을 찾아주는 시스템입니다.**
자막과 화면 설명을 같이 검색합니다. 이번에는 화면 설명을 만드는 3B와 4B 모델 중
무엇을 쓸지 비교했습니다.

**문제는 데이터에 따라 결과가 반대로 나왔다는 점입니다.** AI Hub에서는 4B 쪽이
좋았지만, 실제 긴 영상에 가까운 작은 dev에서는 반대 방향이 나왔습니다. 다만 AI Hub는
짧은 60초 영상이고 질문당 후보가 12개뿐인 반면, dev는 긴 영상이지만 영상이 3편뿐입니다.
그래서 **어느 쪽도 단독으로 최종 결론을 내리기 어렵다**고 판단했습니다.

**그래서 새 데이터로 확인하려 했지만 GT 작성 비용에서 막혔습니다.** 영상 35편과 모델
산출물까지는 만들었지만 175개 라벨 중 20개에서 작업을 중단했고, **그 20개는 분석하지
않았습니다.**

**제대로 재검증하려면 현재 동결한 설계 기준으로 약 1,500개 라벨이 필요합니다.**
남은 한 달 안에는 현실적이지 않아 실행을 보류하고, 대신 **현재 시스템을 제출 가능한
상태로 완성하는 쪽**으로 방향을 바꿨습니다.

**상의하고 싶은 것은 세 가지입니다.**
① 이번 과정에서는 3B/4B 우열을 미해결로 남겨도 되는지,
② 중단한 P2를 비용 제약에 의한 HOLD로 설명해도 되는지,
③ 남은 기간을 모델 비교보다 시스템·보고서 완성에 쓰는 방향이 적절한지.

## 0. 이 프로젝트가 무엇인가 (30초)

**"긴 한국어 영상에서, 말로 물어보면 그 장면이 몇 분 몇 초인지 찾아주는 시스템."**

예: 20분짜리 요리 영상에 `"깻잎 소스를 만드는 장면"`이라고 입력하면
`04:35~04:40` 구간을 1순위로 띄우고, 그 구간부터 바로 재생한다.

작동 방식은 단순하다.

```
영상 → 5초씩 자른다 → 각 구간마다 두 종류의 글을 만든다
                        ├ 자막 : 말소리를 받아쓴다        (Whisper)
                        └ 캡션 : 화면을 보고 설명을 쓴다   (VLM = 이미지 읽는 AI)
     → 두 글을 각각 숫자 벡터로 바꿔 저장한다               (임베딩)
     → 사용자 질문도 같은 방식으로 벡터로 바꿔서
     → 가장 비슷한 구간을 순위로 내놓는다
```

**핵심 질문은 하나다: "화면 설명(캡션)을 쓰는 AI를 무엇으로 할 것인가."**
현재 쓰는 것은 `Qwen2.5-VL-3B`(3B = 30억 파라미터), 후보는 더 큰 `Qwen3-VL-4B`다.
**이번 기간의 절반은 이 둘 중 뭐가 나은지를 가리려는 시도였다.**

## 0-1. 이 문서에 나오는 용어 6개

| 용어 | 뜻 |
|---|---|
| **구간(세그먼트)** | 영상을 5초씩 자른 조각. 검색 결과의 최소 단위 |
| **캡션** | 화면을 보고 AI가 쓴 설명문. **여기가 이번 비교 대상** |
| **자막** | 말소리를 받아쓴 글 (Whisper STT) |
| **MRR** | 성적표. 정답 구간이 1등이면 1.0, 2등이면 0.5, 4등이면 0.25. 질의 전체 평균 |
| **GT(정답 라벨)** | "이 질문의 정답은 몇 초 구간"이라고 사람이 미리 적어둔 것. **평가하려면 반드시 필요** |
| **사전등록** | 실험 결과를 보기 **전에** 판정 기준을 문서로 못박고 커밋하는 것. 결과 보고 기준을 바꾸는 것을 막는 장치 |

> **MRR 감 잡기.** MRR이 0.03 오른다 = 대략 **100개 질문 중 6개에서 정답이
> 2등 → 1등으로 올라간 정도**. 작아 보이지만 검색에서는 의미 있는 크기다.

## 2. 흐름 A — 3B vs 4B, 결과가 정반대로 나온다 (08-17~18)

### 2-1. 무엇을 비교했나

**바꾼 것은 캡션 쓰는 AI 하나뿐이다.** 나머지(자막·검색 코드·평가 방식)는 전부 고정.
실제로 자막만 켜고 재보니 세 조건의 점수가 **완전히 같았다**(dev 96질의 자막 단독
0.4144 — 이 값은 dev 기준이다. AI Hub 자막 단독 baseline 0.4107과 다른 데이터셋이다) — 캡션 말고는
아무것도 안 바뀌었다는 기계적 확인이다.

비교는 **캡션만 켜고**(자막 끔) 한다. 둘을 섞으면 캡션 쪽 차이가 절반으로 희석돼
안 보이기 때문이다.

### 2-2. 두 모델이 실제로 어떻게 다른가 — 캡션 실물

> **예시 선택 규칙(출력을 보기 전에 고정).** ① 위치 기준 — 영상 ID 사전순 첫 영상의
> 첫 질의 ② 순위 차이가 가장 큰 사례를 **양쪽 방향에서 하나씩**(동률이면 ID 사전순).
> **내용을 보고 고르지 않았다.** ②는 극단 사례이므로 대표성이 없다.
> 이 예시는 서술용이며 모델 선택·튜닝 근거로 쓰지 않는다.
> 규칙은 추출 스크립트에 코드로 박혀 있다 —
> `docs/probes/caption_example_extract.py` (검색·평가 모듈 import 0, 저장된 산출물만 읽음).
>
> **화면 사진은 같은 스크립트가 `docs/probes/_scratch/caption_examples_frames/`에 모은다**
> (캡션 생성에 실제로 쓰인 `rep_frame` 원본). 이 폴더는 **git 미추적**이다 — AI Hub
> 프레임은 재배포 권한이 확인되지 않았고 얼굴이 식별 가능하다. 저장소에 올리지 않는다.

먼저 전체 경향 하나. **AI Hub 2,328구간 평균 캡션 길이는 3B 131.4자, 4B 82.0자다.**
4B가 38% 짧다.

#### 사례 ① — 순위가 크게 갈린 경우 (4B 쪽)

```
질의        "여자가 몸을 숙인다"          정답 = 6번 구간 (30~34초)
3B 순위     12위 / 12개 중  → 점수 0.083
4B 순위      1위           → 점수 1.000
화면        B_4B우세__D3_DR_0922_000283_seg06.jpg
            (자물쇠가 빽빽한 난간 앞에서 여성이 상체를 앞으로 숙이고 있다)
```

| | 캡션 |
|---|---|
| **3B** (167자) | 여성은 검은색 재킷을 입고 있으며, 그녀는 다소 놀란 듯한 표정으로 **주변을 살피고** 있습니다. 그녀의 앞에는 다양한 색상과 모양의 사랑의 문구가 달린 열쇠가 걸려 있는 금속 철제 장식이 보입니다. 배경은 푸른 나무와 햇빛이 비치는 풍경으로, 여성이 있는 공간은 아름다운 자연과 조화를 이루고 있습니다. |
| **4B** (62자) | 여성이 빨간색과 다양한 색상의 애정을 상징하는 잠금장치들이 가득한 금속 링 위에서 **몸을 기울이며** 바라보고 있다. |

**여기서 점수가 갈리는 지점이 정확히 보인다.** 질문은 `"몸을 숙인다"`인데,

- 4B는 **`몸을 기울이며`** 라고 썼다 → 질문과 의미가 가깝다 → **1위**
- 3B는 옷·표정·배경을 길게 썼지만 **몸의 자세를 아예 안 썼다** → **꼴찌(12위)**

**3B 캡션이 틀린 게 아니다. 화면 설명으로는 오히려 더 자세하다.**
다만 **질문이 묻는 "동작"이 그 안에 없어서** 검색에서 못 찾는다.

#### 사례 ② — 반대 방향 (3B 쪽)

```
질의        "여자가 주위를 둘러본다"        정답 = 0번 구간 (0~4초)
3B 순위      1위 → 1.000
4B 순위     12위 → 0.083
```

| | 캡션 |
|---|---|
| **3B** (136자) | 화면에는 나무로 만든 야외 공간이 보입니다. 한 여성이 왼쪽으로 향해 걸어가며, 그녀는 긴 머리를 가지고 있습니다. … |
| **4B** (184자) | 숲 속에 있는 목재 구조의 편백으로 된 발코니에서 **세 명의 사람이** 서 있거나 앉아 있다. 왼쪽에는 긴 검은 머리를 가진 여성이 어깨를 살짝 뒤로 젖히고 서 있으며, 그녀는 어깨에 백색 가방을 메고 있고 … 중앙에는 나무 기둥 사이에 앉아 있는 남성이 파란색 배낭을 메고 있고, 머리 위에 흰색 모자를 ▮*(글자 수 상한에 걸려 잘림)* |

여기서는 **4B가 화면 전체를 너무 자세히 적었다.** 세 사람의 옷·가방·자세를 나열하는
바람에 **질문이 가리키는 "그 여자"의 비중이 묻혔고**, 길이 상한(128토큰)에 걸려
문장이 중간에 잘리기까지 했다.

> 참고로 3B 캡션에도 결함이 있다 — 같은 문장에 일본어 문자가 섞여 있다
> (`잎っぱ라진`). 자동 오염 검출기의 기준(가나·한자 3자 이상)에 **2자라서 안 걸린다.**
> 이런 미검출 사례가 남아 있다는 것 자체가 캡션 품질의 상한을 보여준다.

#### 정리 — 성향 차이

| | 3B (현행) | 4B (후보) |
|---|---|---|
| 길이 | 길다 (평균 131자) | 짧다 (평균 82자) |
| 쓰는 내용 | 옷·색·배경을 **나열** | **동작·자세**를 압축해서 |
| 잘 맞히는 질문 | 사물·배경을 묻는 질문 | 동작을 묻는 질문 |
| 실패 방식 | 동작을 안 써서 놓친다 | 너무 많이 써서 핵심이 묻히거나 잘린다 |

> 길이 수치(131자 / 82자)는 2,328구간 실측이다. **성향 서술은 위 예시에서 보이는
> 경향이고, 별도로 측정한 값이 아니다.**

#### 그래서 전체 점수 차이는 왜 작은가

```
1,086개 질문 중
   4B가 더 높은 순위    457개 (42.1%)
   3B가 더 높은 순위    367개 (33.8%)
   완전히 동일          262개 (24.1%)
```

**질문마다 이기는 쪽이 다르고 서로 상쇄된다.** 그 상쇄하고 남은 것이
평균 +0.031이다. 즉 **"4B가 전반적으로 낫다"가 아니라 "이기는 질문이 조금 더 많다"**
수준이고, 그래서 **어떤 질문이 많이 들어있는 데이터를 쓰느냐에 따라 승자가 바뀐다.**

이게 다음 항목의 부호 역전을 이해하는 열쇠다.

### 2-3. 문제 — 데이터를 바꾸면 승자가 바뀐다

`Δ` = 4B 점수 − 3B 점수. **양수면 4B 승, 음수면 3B 승.**

| 어떤 데이터로 쟀나 | Δ | 95% 신뢰구간 | 결론 |
|---|---|---|---|
| AI Hub (공개 데이터셋) 1,086질문 | **+0.031** | [+0.008, +0.054] | **4B 방향의 차이 확인** |
| dev (우리 영상) 96질문 | **−0.090** | [−0.211, −0.028] | **3B 방향의 차이 관찰 — 소규모 진단 결과** |

**두 데이터에서 차이의 방향이 반대로 나타났다.** 이게 이번 기간 전체의 출발점이다.

> dev는 영상이 3편(cluster 3)이라 신뢰구간 자체를 진단적으로만 읽어야 한다.
> **"3B가 이겼다"로 쓰지 않는다** — 뒤의 결론과 충돌한다.

**dev 96질문을 질문 유형별로 쪼개면 방향이 갈린다.**

| 질문 유형 | 개수 | Δ(4B−3B) | |
|---|---|---|---|
| **장면형** (화면에 뭐가 보이나) | 38 | **+0.013** | 4B가 근소하게 앞섬 |
| 자막형 (누가 뭐라고 말하나) | 24 | −0.041 | |
| **복합형** (말+화면을 함께 봐야 함) | 34 | **−0.241** | **여기가 −0.090 전체를 끌고 간다** |

앞의 캡션 예시와 맞물린다. **AI Hub에는 `"여자가 몸을 숙인다"`처럼 짧은 동작·장면
서술형 질문이 많이 보이지만, 전체 질문에 유형 라벨이 없어 정확한 구성 비율은 확인하지
못했다.** 따라서 이것은 **방향이 갈리는 이유의 가능한 설명 중 하나이지, 확인된 원인이
아니다.**

> 다만 "새 데이터를 만들 때 질문 유형 구성을 반드시 맞춰야 한다"는 설계 요구사항은
> 여기서 나왔다.
>
> 이 층 구분은 **결과를 보고 만든 게 아니라** 라벨 파일에 원래 있던 값이고,
> 코드가 다른 축으로 쪼개는 것을 막고 있다.

### 2-4. 두 데이터는 무엇이 다른가

| | AI Hub | dev (우리 영상) |
|---|---|---|
| 어디서 났나 | 공개 데이터셋 (남이 만든 것) | 우리가 직접 수집한 유튜브 영상 |
| 정답 라벨 | 데이터셋 제공자가 붙임 | 우리가 직접 확인해서 붙임 |
| 영상 1편 길이 | **60초** | **12~26분** |
| 규모 | 194편 · 2,328구간 | 3편 · 612구간 |
| **질문 하나당 후보 구간** | **12개** | **149~314개** |
| 아무렇게나 찍었을 때 점수 | **0.26** | **0.02~0.04** |
| 자막 상태 | 69%가 빈칸, 28편은 자막 자체가 없음 | 정상 |

읽는 법 네 가지.

**① 문제 난이도가 다르다.** AI Hub는 **12개 중 하나 고르기**, dev는 **300개 중 하나
고르기**다. AI Hub는 후보가 12개뿐이라 **무작위 기준도 약 0.26으로 높다.**
따라서 **절대 MRR을 실제 긴 영상 검색 성능처럼 읽으면 안 된다.**

**② 60초 클립은 장면이 하나뿐이다.** 구간끼리 서로 구별이 안 된다(캡션끼리 비슷한
정도가 AI Hub 0.76, 우리 영상 0.56 — 높을수록 서로 안 구별됨). 즉 AI Hub는
**"긴 영상에서 원하는 순간 찾기"라는 우리 과제와 문제 성격 자체가 다르다.**

**③ 정밀도가 정반대다.** AI Hub는 194편이라 오차범위 ±0.02로 좁고, dev는 3편이라
±0.09로 넓다. **dev는 이 정도 크기의 차이를 판정할 능력이 애초에 없다** — 그래서
dev 숫자는 공식 판정에 쓰지 않고 진단용으로만 쓴다.

**④ AI Hub는 이미 한 번 썼다.** 모델 후보를 고를 때 쓴 데이터라, 같은 데이터에서
나온 결과를 "독립적인 확인"으로 셀 수 없다.

### 2-5. 다른 설명 가능성을 하나씩 잘라냈다

| 의심 | 검증 결과 |
|---|---|
| 자막과 섞느라 이득이 사라진 건가 | **아니다** — 캡션만 켜도, 섞는 비율을 전부 훑어도 부호 그대로 |
| 섞는 비율(α)이 3B에 맞춰져 있어서인가 | **아니다** — 다시 탐색해도 부호 안 뒤집힘 |
| 모델 압축(4bit) 때문인가 | **아니다** — 압축 없이 재서도 동일 |
| 후보 구간 수 차이(12개 vs 300개) 때문인가 | **부분 기여 가능. 그러나 부호는 설명 못 함** |
| 모델 파일·프롬프트가 서로 달랐나 | **아니다** — 두 실험의 가중치 해시·프롬프트 해시가 완전 동일 |
| 차이가 어디에 몰려 있나 | **4B 쪽에 집중** (국소화 완료) |

부수 성과 하나: **같은 서버·같은 코드면 캡션 생성은 매번 똑같이 나온다**는 것을
655구간에서 확인(완전 일치). 이전에 "생성이 들쭉날쭉하다"고 쓰던 서술을 문서에서 지웠다.

### 2-6. 결론

**기존 두 데이터로는 진짜 승자를 못 가린다.** 하나는 우리 과제와 다른 쉬운 문제이고
이미 썼으며, 다른 하나는 영상 3편이라 정밀도가 없다.
**→ 우리 과제와 같은 성격의 긴 영상으로, 판정 가능한 규모의 새 데이터가 필요하다.**

이것이 다음 두 흐름(B, C)의 출발점이다.

## 3. 흐름 B — 새 데이터 만들기 (08-20~24) → **중단**

### 3-1. 한 것

| 단계 | 상태 |
|---|---|
| 영상 35편 고르기 (규칙을 먼저 정하고 기계적으로 선택) | 완료 |
| 다운로드·출처 기록·영상 형식 검증 | 완료 |
| 3B용·4B용 캡션 두 벌 생성 + 색인 | 완료 (검증 17항목 통과) |
| 질문 175개 배정 (복합 62 / 자막 44 / 장면 69) | 완료 |
| **정답 라벨 작성** | **20 / 175에서 중단** |
| 검색 실행·평가 | **한 번도 안 함** |

### 3-2. 왜 멈췄나

**정답 라벨 1개 = 영상을 직접 보면서 "이 질문의 답은 여기"라고 확인하는 작업**이다.
**이번 평가에서는 정답 위치를 사람이 원본 영상에서 확인해야 했다.** 자동 모델 결과를
그대로 정답으로 쓰면 평가 대상 시스템과 독립된 GT라고 보기 어려워서 사용하지 않았다.

**155개가 남았고, 이 속도로는 남은 기간에 못 끝낸다.**

여기서 흔한 유혹은 **"그럼 175개를 50개로 줄이자"**인데, 이건 금지돼 있다.
**규모를 결과 보고 조정하면 원하는 결론이 나올 때까지 조정하는 것과 구분이 안 된다.**
그래서 **줄이지 않고 멈췄다.**

### 3-3. 멈추는 방식도 규율대로 했다

```
1  라벨 작성 프로그램 정상 종료 (포트 닫힘 확인)
2  종료 전후 파일 해시 동일 확인 — 종료 중 덮어쓰기 0건
3  작업 파일은 수정하지 않고 상태만 기록 · 관련 산출물 8종 해시 동결
4  "채점 결과를 안 봤다"를 항목별로 확인 (검색 실행·점수 계산 전부 false)
```

**작성한 20개는 어떤 분석에도 쓰지 않는다.** 20개만 보고 결론을 내면
"유리한 20개를 골랐다"와 구분이 안 되기 때문이다.

이것을 **"실패한 실험"이라고 부르지 않는다** — 기록상 명칭은
**"라벨 비용 때문에 중단(annotation-cost-driven HOLD)"**이다.

## 4. 흐름 C — 제대로 결판내려면 얼마가 드나 (08-24)

P2가 막힌 뒤, **"그럼 확실히 판정하려면 데이터가 얼마나 필요한가"를 채점 결과와
무관하게 계산**했다.

### 4-1. 결정 4건을 결과 보기 전에 못박았다

| | 결정 | 값 |
|---|---|---|
| 0 | **얼마나 좋아져야 바꿀 가치가 있나** | MRR **+0.02 초과** (≈ 100질문 중 4개가 2등→1등) |
| A | 얼마나 정밀하게 재야 하나 | 오차범위 **±0.02** |
| B | **그러려면 데이터가 얼마나 필요한가** | **영상 300편 × 질문 5개 = 1,500개 라벨** |
| C | 누가 라벨을 다나 | **외부 전문 작업자에게 의뢰** |
| D | 실행 | **보류** (병목: 작업자 섭외·영상 반출 권한) |

> **+0.02는 데이터가 알려준 값이 아니라 "이 정도는 좋아져야 교체할 만하다"는
> 우리가 정한 정책 기준**이다. 그리고 "1,500개면 반드시 판정된다"는 뜻도 아니다.
> 두 표현 모두 문서에 명시했다.

### 4-2. "4B는 무거워서 비싸다"가 사실인지 실제로 쟀다

실제 배포 노트북(RTX 3060 Laptop, VRAM 6GB)에서 양쪽 동일 조건으로 측정.
**캡션 내용은 저장하지 않고 속도·메모리만** 쟀다(성능을 미리 보면 오염이라서).

| | 3B (현행) | 4B (후보) | |
|---|---|---|---|
| 프레임 1장 처리 시간 | 8.06초 | 5.97초 | **4B가 26% 빠름** |
| 캡션 길이 | 133자 | 83자 | 4B가 38% 짧음 |
| VRAM 사용 | 2.64GB | 3.07GB | **4B가 +0.43GB** |
| 모델 파일 크기 | 7.0GB | 8.3GB | **4B가 +1.3GB** |
| 메모리 부족 오류 | 0건 | 0건 | 둘 다 6GB에서 돌아감 |

**판정(기준은 결과 보기 전에 동결): "6GB에 안정적으로 들어가고, 속도도 3B 이상."**

표현을 정확히 고정했다 — **"배포를 막을 요인은 없었고, 자원을 더 먹는 비용은 있다."**
전기요금·비용은 안 쟀으므로 "운영비가 싸다"고는 쓰지 않는다.

**그런데 결과가 역설적이다.**

```
4B의 운영 부담이 작다
   → "조금만 좋아져도 바꿀 만하다"가 된다
   → 그만큼 더 정밀하게 재야 한다
   → 필요한 라벨 수가 늘어난다
```

즉 **4B가 실제 노트북에서도 충분히 돌아간다는 사실은 라벨 부담을 줄여주지 않는다.**
전환 장벽이 예상보다 크지 않다는 것과 평가 비용은 별개다. 반대로 라벨이 힘들다고
"+0.05는 돼야 바꾼다"로 기준을 올리는 것은 금지 — 힘들다는 이유로 기준을 바꾸면
그게 결과 조작이다.

### 4-3. 영상을 외부 작업자에게 보낼 수 있나 — 감사 결과 **0편**

외부에 라벨을 맡기려면 영상을 보내야 하고, 그러려면 권리 확인이 먼저다.
감사 도구를 만들어 기존 35편에 돌렸다.

```
결과   35편 전부 "불명확" · 반출 가능 0편
```

**이건 실패가 아니라 안전장치가 작동한 것이다.** 추가로 확인한 사실:

- **저작권 라이선스가 허용되더라도 영상 속 인물의 초상권·개인정보나 영상에 포함된
  제3자 콘텐츠까지 자동으로 해결되는 것은 아니다.** 그래서 외부 작업자에게 전달할
  권리는 별도로 확인해야 했다.
- **NDA를 맺어도 원래 없던 이용권이 생기지는 않는다.**
- 그래서 **"내가 봐도 되는 권리"와 "사본을 남에게 보낼 권리"를 끝까지 분리**해서
  판정하도록 도구를 고쳤다.

## 5. 흐름 D — 최종 산출물 완성 단계로 전환 (08-25, 오늘)

남은 기간을 고려해 **중심을 "연구 더 하기"에서 "제출 가능하게 만들기"로 옮겼다.**

| 한 것 | 내용 |
|---|---|
| **코드 감사부터** | 실제로 빠진 건 **실행 전 점검 하나뿐**이었다 — 검색·재생·근거 표시는 이미 다 있었다 |
| 데모 진입점 | `scripts/demo.py` — 잘못된 설정으로 시연되는 것을 11개 항목으로 사전 차단 |
| 검색 UI 결함 3건 | 긴 문장이 카드 밖으로 넘침 · 결과 0건일 때 빈 화면 · 잘못된 입력이 서버 오류(500) → 400 |
| 발표용 대비책 | 발표 당일 서버 GPU 없이도 리포트가 뜨도록 사전계산 경로 마련 |
| **외부 영상 실전 테스트** | 우리 데이터가 아닌 유튜브 공개 영상 4편으로 **기능 검증**(성능 측정 아님) |

### 5-1. 외부 영상 테스트 1편차 결과 (오늘)

```
영상   문화포털 공개영상 4분 48초 → 5초씩 58구간
결과   캡션 58/58 · 자막 47/58 · 벡터 정상 · 결측 0
소요   총 538초 (캡션 생성이 489초로 대부분)
재생   클릭한 구간 시작 시각으로 정확히 이동 · 잘못된 요청은 정상적으로 거부
```

**기능 통과.** 남은 3편(10분·21분·68분)은 순서대로 진행 중.

발견 1건: 캡션 하나에 **AI가 지시문에 대답한 문장이 그대로 들어갔고**
("네, 알겠습니다…") 자동 오염 검출기에 걸리지 않았다. 실제 검색 순위에도 영향을 줄
가능성이 있었다.

**한 사례를 본 뒤 검출 규칙이나 표시 방식을 사후 변경하지 않았다.**
semantic smoke를 `REVIEW`로 기록해 한계로 남겼다 — 문제를 발견했다고 즉석에서
기준을 바꾸면 그때부터는 결과를 보고 규칙을 고치는 것이 된다.

## 6. 이 기간에 강화한 실행 규율

연구 결과 오염은 **0건**이지만, 절차 결함은 여러 건 나왔고 **전부 코드로 막았다.**

| 있었던 위험 | 조치 |
|---|---|
| 라벨 작성 도구가 캡션·자막을 볼 수 있었다 (보고 답을 고르면 오염) | 허용 항목만 통과시키도록 강제 |
| 출처 기록 없는 영상이 파이프라인에 들어올 수 있었다 | 첫 단계에서 차단 — **오늘 실제로 걸렸다** |
| 배치 진행 여부를 "프로세스가 살아 있나"로 판단했다 | 완료 표식 + 검증 통과 기준으로 교체 |
| 소규모 테스트를 건너뛰고 본 실행이 가능했다 | 커버리지 선언을 필수로 |
| 라벨 프로그램이 켜진 채로 파일을 줄이려 했다 | 중지 → 적용 → 재시작 순서 강제 |

## 8. 상의하고 싶은 것

**1. 3B↔4B 우열을 이번 과정에서는 미해결로 남겨도 되는가.**
**현재 동결한 P3 설계 기준으로는 300편 × 5질문, 약 1,500개 라벨**과 권리 확인된 영상
300편이 필요하다. 둘 다 남은 기간에 확보 불가로 판단된다. 최종 보고서에는
**"미해결로 남긴 한계 + 결판에 필요한 설계"**로 쓰는 것을 제안한다.

**2. 중단한 실험(P2)을 "비용 제약에 의한 HOLD"로 설명해도 되는가.**
"실패"가 아니라 비용 제약에 의한 중단으로 쓰되, 작성된 20개 라벨은 인용하지 않는다.
이 서술 강도가 적절한지 확인 부탁드린다.

**3. 남은 한 달을 모델 비교보다 시스템·보고서 완성에 쓰는 방향이 맞는가.**
현재는 최종화 쪽으로 방향을 잡았다. **우선순위가 적절한지가 가장 확인받고 싶은
부분이다.**

## 1. test 재평가 — 열되, 큰 모델 확인이 끝난 뒤에 한 번만

### 왜 지금 열면 안 되는가

3번 결정이 1번의 시점을 바꾼다.

지금 4B로 8회차를 돌리고, 나중에 32B가 이겨서 채택하면 **9회차가 필요하다.**
접촉이 한 번 더 늘고, 그때는 "결과를 보고 모델을 바꿨다"는 의심을 받는다.
큰 모델 확인이 끝나 캡션 모델이 최종 확정된 뒤에 열면 접촉은 **8회차 한 번**으로 끝난다.

### 확정 순서

```
1. 큰 모델 확인 (dev + AI Hub, test 미접촉)          ← 3번 결정
2. 캡션 모델 최종 확정
3. test 재평가 8회차 — 프로토콜 d914e79 그대로 1회 연속 실행
     캡션 재생성 → m4 → α·τ 재탐색(dev) → 병합 → M6 → M8 → M9(14B)
```

**`docs/preregistration/test_재평가_프로토콜_2026-08-13.md`의 판정 규칙은 그대로 둔다.** 바뀌는 것은
실행 시점뿐이며, 그 문서는 수정하지 않는다(커밋 후 불변 원칙). 다만 §1의 "캡션 모델
= Qwen3-VL-4B"는 큰 모델 확인 결과에 따라 달라질 수 있으므로, 확정되면 **이 문서에
확정 모델명을 덧붙이고** 프로토콜의 나머지는 그대로 적용한다.

### 이 방식이 방어 가능한 이유

- test는 지금까지 **튜닝 0회**다. 8회차도 튜닝이 아니라 보고용이다
- 바꿀 항목·판정 기준을 결과 보기 전에 고정했고 커밋 해시가 남아 있다
- **§3-3이 핵심이다** — 새 수치가 기존보다 낮아도 채택을 철회하지 않는다. 철회하면
  test로 고르는 것이 되어 튜닝 0회가 깨진다

## 2. 작은 표본의 노이즈를 전제로 삼았던 건 — 상세

### 무슨 일이 있었나

7월 말~8월 초, 같은 모델·같은 설정인데 **노트북에서 만든 캡션이 서버에서 만든
캡션보다 검색 성능이 0.09 높다**는 측정이 나왔다. 이걸 사실로 받아들이자 다음이
따라왔다.

```
노트북 캡션이 더 좋다
  → 노트북에서 생성해야 한다
    → 노트북 GPU가 6GB뿐이다
      → 큰 모델을 못 쓰고, 모델을 압축(4bit)해야 한다
        → 압축 손실 때문에 후보 모델의 이득이 사라진다
```

**즉 노트북 성능 한계가 어떤 모델을 쓸지를 결정하는 상태**가 며칠 이어졌다.

### 왜 착각이었나 — 검출 한계(MDE)

측정에는 **검출 가능한 최소 차이**가 있다. 표본이 작을수록 이 값이 커진다.

| 표본 | 검출 한계 | 의미 |
|---|---|---|
| dev 96건 | **±0.086** | 이보다 작은 차이는 노이즈와 구분 안 됨 |
| AI Hub 562건 | **±0.036** | 0.036 이상이면 검출됨 |

**0.09는 dev의 검출 한계 ±0.086과 거의 같은 크기다.** 즉 실제 효과가 0이어도 그
정도 값은 우연히 나올 수 있다. 그런데 우리는 그 값을 "효과가 있다"로 읽었다.

### 두 번 "재현"했다고 믿었던 것의 정체

당시 두 번 측정해서 두 번 다 비슷한 값이 나왔다. 그래서 재현됐다고 판단했다.
**그런데 두 번 다 같은 dev 96건이었다.** 같은 표본을 두 번 재면 같은 노이즈가 두 번
나온다. 이건 재현이 아니라 **같은 측정의 반복**이다.

재현이 되려면 **다른 표본**이어야 한다.

### 독립 표본에서의 결과

AI Hub 공개 데이터 97편·562건에서 같은 조건으로 다시 쟀다.

```
서버 생성 0.4872    노트북 생성 0.4826
차이 −0.0046   95% 신뢰구간 [−0.027, +0.017]   p = 0.68
```

**차이가 없다.** 그리고 이건 "못 쟀다"가 아니다. 이 표본의 검출 한계는 0.036인데
신뢰구간 상한이 +0.017이므로, **0.09는 확실히 배제된다.**

*이 검정은 노트북에 유리하게 설계돼 있었다는 점도 중요하다(사전 등록 §7-d).
유리한 조건에서도 아무것도 안 나왔으므로 결론이 더 강하다.*

부수적으로, 기계를 바꾸면 캡션 문장의 **77%가 실제로 달라진다**(완전일치 23.2%).
그런데 검색 성능은 안 달라진다. **표현이 바뀌는 것이지 품질이 바뀌는 게 아니다.**

### 앞으로의 판단 기준 (이번에 정한 것)

| 규칙 | 내용 |
|---|---|
| R1 | 수치를 의사결정에 쓰기 전에 **그 표본의 검출 한계를 먼저 계산**한다 |
| R2 | 관측된 차이가 검출 한계와 비슷한 크기면 **"효과 있음"으로 읽지 않는다** |
| R3 | 재현은 **다른 표본**에서만 인정한다. 같은 표본 재측정은 재현이 아니다 |
| R4 | 배포·채택 결정은 **독립 표본 확증 이후**에만 한다 |

R3가 이번 사건의 핵심이다. 나머지 셋은 알고 있었는데 R3를 안 지켰다.

*이 규칙은 이미 `CLAUDE.md` 판단 기준과 `DESIGN_SPEC 8-7`(후보 모델 검증 규약
2항 "검출 한계 병기")에 반영돼 있다.*

## 3. 더 큰 모델 확인 — 설계

### 먼저 알아야 할 것: 8B는 이미 졌다

dev 스윕에서 크기를 한 번 올려봤고 **더 나빴다.**

| arm | 캡션 단독 MRR | 생성 시간 |
|---|---|---|
| Qwen3-VL-**4B** / P1 | **0.5522** | 1,644초 |
| Qwen3-VL-**8B** / P1 | 0.5246 | 1,722초 |
| Qwen3-VL-8B / P0 | 0.4627 | 1,527초 |

즉 이 과제에서 "크면 좋다"는 4B→8B 구간에서 이미 한 번 깨졌다. 그래도 8B는
32B까지의 중간 지점이므로, 더 큰 쪽에서 뒤집힐 가능성을 배제하지는 못한다.
**그래서 확인한다.**

### 후보와 하드웨어 제약

Qwen3-VL 계열은 2B · 4B · 8B · 30B-A3B(MoE) · 32B가 있다.
서버는 RTX 4090 **24GB** 한 장이다.

| 후보 | bf16 추정 | 24GB 적재 | 4bit 추정 |
|---|---|---|---|
| Qwen3-VL-32B | 약 64GB | **불가** | 약 18~20GB (가능) |
| Qwen3-VL-30B-A3B (MoE) | 약 60GB | **불가** | 약 17GB (가능) |

**둘 다 4bit로만 올라간다.** 이게 이번 비교의 최대 난점이다.

### 정밀도 교란을 어떻게 다룰 것인가

현행 후보 4B는 **bf16**로 돈다. 32B를 **4bit**로 돌려 비교하면 모델 크기 효과와
양자화 손실이 섞인다. 이미 한 번 겪은 교란이다.

4B에서 실측된 양자화 손실은 **−0.0604**다(0.5522 → 0.4918).

따라서 아래를 **같은 세션에서** 함께 돌린다 [규약 4항 동일 환경 대조군].

| arm | 목적 |
|---|---|
| Qwen3-VL-4B / P1 **bf16** | 현행 기준선 |
| Qwen3-VL-4B / P1 **4bit** | 4B의 양자화 손실 재확인 |
| Qwen3-VL-32B / P1 **4bit** | 후보 |
| Qwen3-VL-30B-A3B / P1 **4bit** | 후보(MoE, 활성 3B라 속도 이점) |

**판정은 4bit끼리 비교로 한다** — 4B-4bit 대비 32B-4bit가 이기는지. 그래야 크기
효과만 남는다. bf16 4B와의 비교는 참고로만 병기한다.

### 프롬프트 재탐색 [규약 3항]

P1은 4B에 맞춰 고른 프롬프트다. 큰 모델에 불리할 수 있다. 다만 P0~P4 전체 격자를
32B로 돌리면 시간이 감당이 안 된다(아래).

**타협: P1 + P4 두 개만 돌린다.** P4는 문장 수 제한이 없어 큰 모델에 여지를 주는
프롬프트이고, 7B가 P4에서만 자기 최고를 낸 전례가 있다. **재탐색을 축소했다는
사실을 결과에 명시한다.**

### 소요 추정

4B bf16이 655장에 1,644초(2.5초/장)였다. 32B-4bit는 4~8배로 본다.

| arm | 추정 |
|---|---|
| 4B bf16 / 4B 4bit (P1) | 각 30~40분 |
| 32B 4bit × P1·P4 | 각 2~4시간 |
| 30B-A3B 4bit × P1·P4 | 각 1~2시간 (활성 3B) |
| **합계** | **약 8~14시간** |

하룻밤 배치 한 번 분량이다. **속도는 기각 사유로 쓰지 않는다**(CLAUDE.md 판단 기준).

### 판정 기준 (결과 보기 전 확정)

- **주 지표: 캡션 단독 α=0.0 MRR, dev 96건** [규약 1항 채널 격리]
- **1차 관문(dev):** 32B-4bit 또는 30B-A3B-4bit가 **4B-4bit**를 이길 것
- **2차 관문(독립 확증):** dev에서 이긴 arm만 AI Hub 1,086건에서 재측정.
  거기서도 신뢰구간이 0을 배제해야 채택
- **검출 한계 병기 필수** — dev 96의 MDE는 ±0.086이다. 그보다 작은 차이는
  "이겼다"고 쓰지 않는다 [§2 R2]
- 어느 후보도 2차 관문을 통과하지 못하면 **4B로 확정**하고 그대로 기록한다

*1차에서 4B-bf16과 직접 비교하지 않는 이유: 양자화 손실 −0.06이 섞여 큰 모델이
부당하게 진다. 최종 배포 판단은 2차 통과 후 bf16 적재 가능 여부와 함께 따로 본다.*

### 이 결정의 비용

큰 모델 확인이 끝날 때까지 **test 재평가가 미뤄진다**(§1). 확인에 하룻밤,
확증에 반나절이 더 든다. 그 대신 test 접촉이 8회차 한 번으로 끝난다.

## 4. M9 판정자 교체 + 기존 수치 재산출

**재산출한다.** 이미 프로토콜 `d914e79` §2 8단계와 §3-6에 등록돼 있어 추가 접촉이
발생하지 않는다 — 8회차 연속 실행에 포함된다.

| 항목 | 처리 |
|---|---|
| 판정자 | Qwen2.5-7B → **Qwen2.5-14B (4bit)** |
| 기존 test coverage 수치 | **폐기.** 탈락한 계측기의 출력이며, 사유를 문서에 남긴다 |
| 기존 test groundedness 수치 | 7B도 게이트를 통과했으므로 **신·구 병기**해 판정자 교체 영향을 보인다 |
| 병기할 한계 | 14B가 통과선 0.75를 0.767로 겨우 넘겼다는 점, 셀당 60문항뿐이라는 점 |

게이트 실측치(`_scratch/judge_gate_models.json`, 셀당 60문항):

| 판정자 | coverage 양성 | coverage 음성 | groundedness 양성 | 판정 |
|---|---|---|---|---|
| Qwen2.5-7B | 0.550 | 0.983 | 0.817 | **coverage 탈락** |
| kanana-1.5-8B | 0.417 | 1.000 | 0.850 | **coverage 탈락** |
| Qwen2.5-14B (4bit) | **0.767** | 0.933 | **1.000** | 통과 |

*14B만 메모리 때문에 4bit로 돌렸다. 양자화는 보통 불리하므로, 불리한 조건에서
통과했다는 점은 결론을 약화시키지 않는다.*

## 5. 갱신된 전체 순서

```
[A] GPU 없이 — 진행 중
    ✔ 재캡셔닝 사전 게이트 + 전건 실패 저장 금지        2e33fd0
    ✔ M8 절단 원인 규명 + 개선 기준 사전 등록           ec1c5c2
    ✔ M8 입력 CJK 제거 + 청크 조기 종료 감지            3c8a0ba
      서버 손상 7편 복구 · 프레임 1,518장 업로드
      질의 패러프레이즈 강건성 (dev 96, 노트북)
      작업현황 갱신

[B] GPU 확보 — 1차: 큰 모델 확인          약 8~14시간   ← 3번 결정
      4B bf16 · 4B 4bit · 32B 4bit · 30B-A3B 4bit (P1·P4)
      dev 96 캡션 단독 판정 → 통과 arm만 AI Hub 확증

[C] GPU — 2차: M8 개선                    약 2~3시간
      dev 3편 개선 전/후 리포트 → 사전 등록 관문 판정

[D] GPU — 3차: test 재평가 8회차          약 4.5시간    ← 1번 결정
      캡션 모델 확정 후 1회 연속 실행. M9는 14B로 재산출  ← 4번 결정
```

**[D]는 [B]가 끝나기 전에 시작하지 않는다.** 이 순서가 test 접촉을 한 번으로
묶는 유일한 방법이다.

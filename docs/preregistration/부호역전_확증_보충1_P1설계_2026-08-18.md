## 1. PRIMARY estimand — `I_pool` 하나로 고정한다

MRR을 나열하지 않고 **풀 크기 × 모델 상호작용**을 직접 잰다. 캡션 단독(α=0)이다.

```
D_small = MRR_caption(4B, 후보 12개)  −  MRR_caption(3B, 후보 12개)
D_large = MRR_caption(4B, 전체 풀)    −  MRR_caption(3B, 전체 풀)
I_pool  = D_large − D_small
```

**사전 예측 방향: `I_pool < 0`** — 풀이 커질 때 4B가 3B보다 상대적으로 더 손해를 본다는
가설이다.

| 데이터셋 | `D_small` | `D_large` |
|---|---|---|
| dev 96 | **새로 계산** (12 후보) | 기존 −0.0903 (149~314 후보) |
| AI Hub 1,086 | 기존 +0.0310 (영상 내 12 후보) | **새로 계산** (2,328 후보) |

**두 데이터셋에서 조작 방향이 반대다** — dev는 줄이고 AI Hub는 늘린다. 같은 가설이
양쪽에서 같은 부호의 `I_pool`을 예측한다.

### 1-1. 판정식 — 결과 보기 전에 고정

| 결과 | 읽는 방식 |
|---|---|
| 두 데이터셋 모두 `I_pool < 0` | **양방향 조작 증거.** 풀 크기 민감도를 부호 역전의 plausible contributor로 지지한다 |
| 한쪽만 `I_pool < 0` | **partial support.** 어느 쪽이 맞았는지 적고, 다른 쪽 조작이 무엇을 같이 바꿨는지 규명한다 |
| 양쪽 모두 `I_pool ≥ 0` | **가설 미지지.** 남은 후보(type·도메인·길이)로 넘어간다 |
| 두 데이터셋이 반대 부호 | **가설과 어긋남.** 그대로 기록한다. 한쪽을 골라 쓰지 않는다 |

```
판정은 I_pool 점추정 부호로만 한다
magnitude threshold를 결과 보고 만들지 않는다 — "충분히 큰 I_pool" 같은 기준을 신설하지 않는다
CI: dev는 3 cluster이므로 진단용만. AI Hub는 194 cluster이므로 video-cluster CI를 보고한다
```

### 1-2. P1은 확증이 아니다 — 보고 상한을 미리 박는다

dev·AI Hub는 **둘 다 소진된 표본**이다. P1은 후보 집합만 재조작하는 mechanism
diagnostic이다. 결과가 예측과 완전히 맞아도 쓸 수 있는 최대치는 이것이다.

> **"두 기존 표본에서 candidate-pool manipulation이 사전 예측 방향으로 4B−3B contrast를
> 이동시켰다. 이는 pool-size sensitivity를 sign reversal의 plausible contributor로
> 지지하며, fresh long-form confirmation에서 검증할 조건을 구체화한다."**

**금지 문장** — "candidate pool size가 부호 역전의 원인으로 확정됐다", "유일한 원인이다",
"이로써 4B를 채택/기각한다".

## 2. 조작 정의 — 이름이 조작 내용과 일치해야 한다

본 사전등록의 `GT 포함 12세그먼트 창`은 풀 크기와 **negative의 시간적 locality**를 동시에
바꾼다. 인접 세그먼트는 화면이 비슷해 난이도가 다르다. 그래서 조작을 둘로 나눈다.

### 2-1. `P1a_pool_size_random_negatives` — **PRIMARY**

```
gold positive     전부 보존
negative 11개     같은 영상의 원래 후보 풀에서 결정적 규칙으로 선택
선택 규칙         sha256(f"{run_tag}|{query_id}|{video_id}|{seg_idx}") 오름차순 상위 11개
                  arm·캡션·임베딩·점수·순위를 입력으로 받지 않는다
반복              단일 결정적 선택 (난수 seed 없음 — 해시가 결정적이다)
```

**이것이 풀 크기 조작의 주 정의다.** locality를 바꾸지 않는다.

### 2-2. `P1a_local_window_12` — SECONDARY

```
gold positive     전부 보존
후보              GT를 포함하는 연속 12세그먼트 창
창 위치           GT를 포함하는 시작점 중 결정적 선택 (해시 순서로 1개)
```

**AI Hub의 실제 구조(60초 영상 = 연속 12세그먼트)를 모사한다.** 그래서 이름에
`local_window`를 박는다 — **`pool_size_only`라고 부르지 않는다.** 이 변형은
풀 크기 **+ locality**를 동시에 바꾼다.

> **두 변형의 차이가 locality 기여분의 추정치다.** 그 차이를 인과로 주장하지 않고
> 기술값으로만 적는다.

### 2-3. `P1b_cross_video_pool_expansion` — AI Hub 확대

```
후보     AI Hub 194영상 2,328세그먼트 전체 (영상 경계 제거)
```

**AI Hub 영상은 12세그먼트뿐이라 영상 내 확대가 불가능하다.** 따라서 확대는 필연적으로
영상 경계를 넘고, **풀 크기 + 영상 간 혼동**을 동시에 바꾼다. 이름에 `cross_video`를
박는다.

### 2-4. 공통 규칙 — 결과 보기 전에 고정

```
gold이 12개를 넘는 질의   fail-closed. 그 질의를 제외하고 제외 수·query_id를 보고한다
                          (dev GT 세그먼트 median 1 · max 5이므로 발생하지 않을 전망)
12 이외의 풀 크기         §4의 사전 선언 격자만 쓴다. 결과를 보고 격자를 늘리지 않는다
평가                      캡션 단독 α=0.0만. α·τ를 읽지 않는다
```

## 3. 실행 가능성 — **임베딩이 저장돼 있지 않다.** 좁은 완화 1건

실측(2026-08-18):

```
저장됨      캡션 텍스트 전량 — prec3_0818b 3 arm · AI Hub 2×2 4 arm (2,328×4)
            arm별 provenance (model_revision 포함)
저장 안 됨  임베딩, 질의별 전체 순위, 점수 행렬
            (m6_evaluate는 rank·mrr만 남긴다)
```

**따라서 후보 집합을 바꿔 MRR을 다시 계산하려면 저장된 캡션 텍스트를 다시 임베딩해야
한다.** 본 사전등록 §1-3의 "새 embedding 생성 없음"을 그대로 지키면 P1은 실행 불가다.

### 3-1. 완화 범위 — 정확히 이것만

| | |
|---|---|
| 여전히 금지 | 새 캡션 생성, VLM 추론, 캡션 텍스트 수정, 프롬프트 변경 |
| 여전히 금지 | 후보 선택에 arm·캡션·임베딩·점수·순위를 쓰는 것 |
| 여전히 금지 | 확정 인덱스(`work/*/emb_*`)에 쓰기, `alpha_search_dev.json`·`eval_test.json`에 쓰기 |
| **허용** | 저장된 캡션 텍스트를 **동일 embedder(KURE-v1)로 다시 임베딩**하는 것 |
| 필수 | 캡션 텍스트 SHA256을 산출물에 기록 |

### 3-2. 재현 게이트 — 완화를 검증 가능하게 만든다

**전체 풀 조건에서 재계산한 MRR이 저장된 값과 일치해야 한다.**

```
dev      재계산 mrr_caption_only  ==  저장값 (4B q4 0.3741 · 4B bf16 0.3650 · 3B 0.4644)
AI Hub   재계산 cap MRR           ==  저장값 (4B/P0 0.5083 · 3B/P0 0.4773)
허용 오차  소수 4자리 완전일치
```

**불일치하면 P1을 FAIL로 보존한다.** 현장에서 허용 오차를 늘려 살리지 않는다.
불일치는 임베딩 경로가 원 실행과 다르다는 뜻이고, 그 상태의 조작 결과는 해석할 수 없다.

> 근거: 같은 서버·같은 commit·같은 경로에서 AI Hub 2,328구간 재생성이 완전일치
> 1.0이었다(CLAUDE.md 실무 규칙). **greedy 파이프라인은 통제된 조건에서 결정적**이므로
> 이 게이트는 통과 가능한 기준이다.

## 5. TDD 계약 — 결과 보기 전에 고정

```
1  후보 선택 함수가 arm·캡션 텍스트·임베딩·유사도·rank·RR을 인자로 받지 못한다
2  같은 질의의 모든 arm이 byte-for-byte 동일한 후보 segment ID 목록을 받는다
3  모든 gold positive가 후보에 보존된다. |gold| > pool_size면 fail-closed
4  P1-b의 2,328 universe가 모든 arm에서 동일하고, segment ID 중복·누락이 없다
5  새 캡션 생성·VLM 추론이 호출되지 않는다 (m3_generate 진입점 호출 금지를 테스트)
6  모듈이 alpha_star·alpha_curve·mrr_alpha_fixed·tau·SECONDARY 키를 읽지 않는다
7  source run id·캡션 텍스트 SHA·후보 구성 규칙 이름·규칙 version을 산출물에 기록한다
8  기록이 없는 parity 필드는 `unknown_not_recorded` — PASS도 FAIL도 아니다 (match: None)
9  CLI를 cp949 stdout 환경에서 subprocess로 실행해 exit 0까지 검사한다
10 재현 게이트(§3-2) 불일치 시 예외로 중단한다 — 조용히 계속하지 않는다
```

**9번은 실제 사고에서 나왔다.** `sign_reversal_diag`가 산출 JSON을 쓴 뒤 stdout에서
죽었다. 연구 결과 손상은 없었지만 **산출물 존재와 run 성공을 분리해 검사해야 한다는
사례**다. CLI 출력을 ASCII-safe하게 유지하는 것이 가장 단순한 해법이다.

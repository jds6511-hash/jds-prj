# I1 detector 재설계 — 사전등록 (2026-08-18)

**이 문서는 결과를 본 뒤 고치지 않는다.** 이탈은 작업현황·결과 문서에 기록한다.
**검증 표본을 아직 만들지 않은 시점에 작성·커밋한다.**

## 0. 무엇이 확정됐고 무엇이 남았나

`docs/재분석_I1검증셋B_2026-08-18.md` 실측:

```
precision  0.9861  CI [0.9254, 0.9975]   scene text 오탐 0건
recall     0.0815  CI [0.0815, 0.0957]   (weighted estimator)
```

현행 `is_corrupted_caption`의 CJK 임계는 **절대 3자**다. 현재 I1a는 **CJK 1~2자
영역에 큰 blind spot**이 있고, C2 표본의 명확한 20건이 전부 drift였다.

> **이번 사이클에서 threshold를 바꾸지 않는다.** 이 문서는 **설계와 검증 절차**를
> 고정하는 것이고, 채택이나 hard gate 승격이 아니다.

## 1. 표본 경계 — **가장 중요한 조항**

> **I1 B단계의 24건은 detector 재설계에 소비된 표본이다.**
> 후보 규칙을 **설계**하는 데 쓸 수 있다(development rule). 그 24건으로 성능을
> **평가하면 순환이다** — 설계에 쓴 표본으로 검증하는 것이기 때문이다.

```
development set   I1 B 24건 + A 116프레임        ← 규칙 설계에만
validation set    새로 표집한 미사용 표본        ← 성능 판정
```

**검증 표본은 이 문서 이후 별도로 표집한다.** 표집 설계(층·쿼터·모집단·seed)를
그 시점에 사전등록하고, **표집 전에 후보 규칙을 확정한다** — 순서를 뒤집으면
표본을 보고 규칙을 고른 것이 된다.

## 2. 후보 규칙 — 두 축으로 분리한다

현행은 하나의 함수가 진단과 hard fail을 겸한다. 그것이 임계 하나에 두 목적을
얹는 원인이다. 2×2 §2-4에서 이미 지적된 분리를 여기서 고정한다.

| 축 | 이름 | 성격 | 후보 정의 |
|---|---|---|---|
| 진단 | `foreign_script_present` | 관측만. 재캡셔닝 트리거 아님 | CJK **≥1자** |
| 실패 | `language_drift` | hard fail. 재캡셔닝 트리거 | **긴 연쇄** 또는 **고비율** |

`language_drift`의 파라미터(연쇄 길이·비율 임계)는 **development set에서 정하고
이 문서에 값을 적지 않는다** — 값을 여기 박으면 그 값 자체가 사전등록이 되어
development 단계에서 조정할 수 없다. 대신 **정하는 절차**를 고정한다.

```
1. development set에서만 후보 파라미터를 탐색한다
2. 선택 근거(무엇을 최대화·제약했는가)를 결과 문서에 남긴다
3. 확정한 값을 **검증 표집 전에** 별도 문서로 커밋한다
4. 그 뒤 validation set에서 한 번만 평가한다
```

## 3. 판정 지표

| | |
|---|---|
| 주 지표 | validation set의 **precision · recall** (셀 가중, weighted estimator) |
| 비교 대상 | 현행 `CJK≥3` 규칙 — **같은 validation set에서 동시에** 잰다 |
| 보고 | 점추정 + CI. 표본이 프레임 클러스터임을 명시 |

**"개선"이라는 말은 현행과 같은 표본에서 동시에 잰 뒤에만 쓴다.** 현행 값은
`0.9861 / 0.0815`이지만 그것은 **development set 수치**이므로 validation set에서
다시 잰다 — 서로 다른 표본의 수치를 비교하지 않는다.

## 4. 하지 않는 것

- **hard gate 승격을 이 사이클에서 하지 않는다.** `language_drift`가 재캡셔닝을
  트리거하게 만드는 것은 **확정 인덱스에 영향을 주는 변경**이라 사용자 승인 + 별도
  사전등록이 필요하다(CLAUDE.md 실무 규칙).
- **캡션을 내용 보고 고치지 않는다.** 어떤 규칙이든 **자동 판정만**이다
  (CLAUDE.md 절대 규칙 2).
- **`4B/P0` 선호를 이 문서로 확정하지 않는다.** 새 detector에서 arm 순위가 어떻게
  되는지는 별도 질문이고, `4B/P0`의 잠정 선호 근거가 **recall 8%인 검출기의 적중 수
  차이**였다는 점은 결과 문서에 남아 있다.
- **비-CJK drift로 확장하지 않는다.** B에서 C0을 직접 보지 않았다(보충2).

## 5. 미규명으로 남기는 것

- **`C1` 1건** — 캡션 CJK가 0인데 I1a가 적중했다. 발화 사유를 규명하지 않았다.
  새 규칙 설계 시 이 경로가 어디서 왔는지 확인한다.
- **`unclear` 비율** — A 16.2%, B 4/24. 대표 프레임 1장이라는 구조적 한계에서 온다.
- **오염과 검색 성능의 인과** — dev 정밀도 3-arm에서 4B의 오염이 현행보다 4~5배
  많고 MRR도 낮았지만(§5-9), 이 배치로 인과를 확정하지 않았다.

## 6. 절차

```
이 문서 커밋
  → development set에서 파라미터 탐색 (24건 + 116프레임)
  → 확정 파라미터를 별도 문서로 커밋
  → validation 표집 설계 사전등록
  → 표집 · 라벨 (라벨 도구는 m5_search·m6_evaluate를 import하지 않는다)
  → validation set에서 현행 vs 신규를 동시 평가, 한 번만
  → 그 결과로 hard gate 승격 여부를 사용자와 판단
```

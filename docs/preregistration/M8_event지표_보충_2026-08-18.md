# 보충 — M8 event 지표의 분모 문제 (2026-08-18)

`M8_구조변경_사전등록_2026-08-16.md`의 **보충**이다. 원 사전등록은 고치지 않는다.
**M8을 아직 한 번도 재실행하지 않은 시점에 작성·커밋한다.**

---

## 0. 먼저 확인한 것 — **정답 사건 목록은 존재하지 않는다**

`event coverage`를 정의하기 전에 분모부터 확인했다.

| 확인 | 결과 |
|---|---|
| 원 사전등록이 정의한 정답 | 사람이 쓴 **사건 목록(event inventory)** — §2-2 |
| 그 목록이 실재하는가 | **아니다.** 원 사전등록 §2-4가 *"정답 사건 목록이 아직 없으므로 역산할 대상이 없다"*고 이미 적었다 |
| 저장소 탐색 | `label_kit/`·`data/`에 사건 목록 파일 없음. `*event*` 전수 검색에서 해당 산출물 0건 |
| 작성 주체 | **사용자**(GT 규칙 — 검색·리포트 결과를 보지 않고 프레임 실물로만) |

> **따라서 `event coverage`의 분모를 M8이 스스로 생성한 event 목록으로 두면
> 자기참조가 된다.** "모델이 무엇을 사건으로 뽑았는가"를 같은 모델 출력으로
> 평가하게 된다. **이번 사이클에서는 event coverage를 정의하지 않는다.**

이건 실패가 아니라 **이 단계의 발견**이다. 억지로 숫자를 만드는 대신 그렇게 적는다.

---

## 1. 그래서 이번 M8 dev 재실행은 **판정이 아니라 예비 실행**이다

원 사전등록이 이미 두 가지를 못박아 뒀고, 둘 다 지금 충족되지 않는다.

| 원 사전등록 | 현재 |
|---|---|
| §3 "구조 선택 판정 표본은 **8~12편**. dev 3편으로는 판정하지 않는다" | dev는 3편 |
| §2-3 관문 C1~C3 (주지표 Event Recall 중앙값) | 정답 목록이 없어 **계산 불가** |
| §5 "dev 3편 **예비 실행**으로 JSON 안정성을 먼저 확인" | ← **이번에 하는 것이 이것이다** |

> **원 사전등록의 C1~C3는 살아 있고 미집행 상태다.** 이번 실행 결과로 그 관문을
> 판정하지 않으며, 관문·임계를 고치지도 않는다.

---

## 2. 이번에 재는 것 — 구조·타임라인 **진단** 지표

전부 `validate_events`가 코드로 판정하는 값에서 나온다. **품질 지표가 아니다.**

| 지표 | 정의 |
|---|---|
| `valid_events` / `rejected_events` | 채택·기각 수 |
| `rejection_reasons` | 9개 사유별 분포(`empty_event`·`no_segments`·`bad_span`·`seg_out_of_range`·`too_many_evidence`·`duplicate_evidence`·`evidence_outside_span`·`foreign_language`·`thin_description`) |
| `span_len_dist` | 사건 span 길이 분포(구간 수) |
| `evidence_per_event_dist` | 사건당 근거 구간 수 분포 |
| `chars_per_evidence` | `len(description) / len(evidence_segments)` 분포 |
| `event_span_overlap` | 사건 간 span 겹침 비율 |
| **`timeline_span_coverage`** | 사건 span들의 **합집합** ÷ 영상 전체 구간 수 |
| `chunk_retries` / `merged_pairs` | 청크 재생성 횟수, 병합된 사건 쌍 수 |
| **catastrophic** | 다른 언어 이탈·조기 종료·반복 루프 발생 영상 수 (원 사전등록 C1과 같은 정의) |

**`timeline_span_coverage`를 `event coverage`라고 부르지 않는다.** 긴 span 하나로
올릴 수 있으므로 **품질이 아니라 진단**이다. 이름에 그 사실을 박아 둔다.
(원 사전등록 §2-1이 `segment coverage`를 내린 것과 같은 이유다 — 번호를 많이
달수록 오르는 지표를 주지표로 두지 않는다.)

---

## 3. GT가 생긴 뒤 쓸 matching 규칙 — **지금 고정한다**

**GT가 아직 없고 M8도 안 돌린 지금 고정하는 것이 요점이다.** 나중에 정하면
목록과 지표를 서로 맞춰 튜닝할 수 있다.

### 3-1. event 단위 (GT 작성 규칙)

```
사건 = 하나의 목적을 가진 연속 행위. 시작·끝 시각과 한 줄 이름을 갖는다.
분리: 행위 주체나 목적이 바뀌면 나눈다.
병합: 같은 목적의 행위가 30초 이내 간격으로 이어지면 하나로 본다.
제외: 인트로·아웃트로·자막만 있는 전환 구간.
경계: 초 단위로 적고 seg_idx 파생은 코드가 한다(gt_seg_idx 파생 규칙과 동일 원칙).
```

### 3-2. matching — **1:1**

```
similarity(R_i, G_j) = temporal IoU(span_i, span_j)
최대가중 1:1 매칭 (generated event 하나는 reference event 하나에만 대응)
```

**단순 "조금이라도 겹치면 covered"를 쓰지 않는다.** 거대한 span 하나가 여러 정답
사건을 먹어 recall을 부풀린다. 1:1이 그것을 막는다.

### 3-3. 주지표 / 부지표

| | 지표 |
|---|---|
| **주** | `event_temporal_alignment` = reference event별 매칭된 temporal IoU의 **macro 평균**(매칭 실패 = 0) |
| 부 | `IoU ≥ θ` event recall (θ = 0.3 · 0.5 · 0.7 **세 값 모두 보고**, 하나를 고르지 않는다) |
| 부 | `timeline_span_coverage` · `compression`(생성 사건 수 ÷ 정답 사건 수) · 구조 지표 전부 |

**주지표를 연속값으로 두는 이유:** 임계 θ를 하나 고르면 그 선택이 결과를 만든다.
원 사전등록이 0.70·2.0에 외부 근거가 없다고 자백한 것과 같은 문제다(§2-4).

### 3-4. 유효 event 범위

평가 대상은 **`validate_events`를 통과한 사건만**이다. 기각분은 penalty로 환산하지
않고 **수와 사유를 병기**한다 — 환산 계수에 근거가 없다.

---

## 4. 이것이 원 사전등록의 무엇을 대체하는가 — **명시한다**

§3의 matching 규칙과 주지표는 원 사전등록 §2-2의 **Event Recall**과 §2-3의
**C2(중앙값 ≥0.70)** 를 대체하는 변경이다. 조용히 바꾸지 않는다.

**사유.** 원 문안의 "정답 사건 중 리포트가 담은 비율"은 **matching 규칙을 정하지
않았다.** 그 상태로는 사건 하나가 여러 정답을 덮어도 recall이 오른다 —
`segment coverage`를 내린 것과 **같은 종류의 결함**이 주지표에 남아 있었다.

**적용 조건.** 이 대체는 **정답 목록이 만들어지고 8~12편이 확보된 뒤** 발효한다.
그 시점에 §3을 담은 **새 사전등록**을 쓰고, 원 문서는 그대로 둔다.
이번 예비 실행에는 §3이 적용되지 않는다(계산할 정답이 없다).

## 6. 그래서 다음 순서

```
1. M8 dev 예비 실행 — 구조·타임라인 진단만. 판정 아님   [GPU 필요]
2. 정답 사건 목록 작성 규칙 확정 → 사용자 작성          [사용자 시간이 병목]
3. dev 8~12편 확보                                     [사용자 시간]
4. §3을 담은 새 사전등록 → 구조 판정
```

**2번이 진짜 병목이다.** I1 프레임 라벨과 같은 줄에 선다. 사건 목록은 검색 라벨과
달리 질의·정답 구간이 필요 없어 **영상당 비용은 낮다**(원 사전등록 §3).

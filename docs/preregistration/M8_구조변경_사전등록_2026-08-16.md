# M8 구조 변경 — 판정 기준 사전 등록 2차 (2026-08-16)

**이 문서는 새 구조를 dev에 돌리기 전에 쓴다.** 아래 기준은 결과를 보기 전에 정했다.

---

## 0. 1차 등록은 어떻게 되는가 — 폐기가 아니라 **판정 실패로 종결**

`docs/M8_개선_사전등록_2026-08-14.md`는 그대로 둔다. 임계를 고치지도 지우지도 않는다.
그 문서의 관문으로 6개 arm을 판정했고 **전부 미달**이었다. 그 결과가 결론이다.

**지표를 바꾸는 것은 그 판정이 끝난 뒤이며, 이유는 결과가 나빠서가 아니라 계측이
의사결정을 지탱하지 못한다는 것이 실측으로 드러났기 때문이다.**

| 무엇이 드러났나 | 실측 |
|---|---|
| 프롬프트 문장 하나로 영상별 커버가 뒤집힌다 | `prefix` arm r1↔r2: +48.3%p / −44.3%p |
| 그런데 무작위가 아니다 | 그리디, 같은 코드·입력이면 저장분과 완전 일치 재현 |
| 최종 커버를 정하는 것은 map이 아니라 reduce | map 294 → reduce 150, map 189 → reduce 59 |
| 방어장치가 새 실패를 만든다 | `no_repeat_ngram=12` 발동 2건 → 2건 다 중국어 이탈 |

*이 절이 없으면 "관문을 못 넘자 관문을 바꿨다"가 된다. 1차 판정 결과(전 arm 미달)를
결과 보고에 그대로 싣고, 그 위에 2차를 쌓는다.*

## 1. 무엇을 바꾸는가

### 1-1. free-form reduce 폐기

```
지금  segments → map(산문) → LLM reduce(산문) → 리포트
새것  segments → map(사건 JSON) → 코드 병합·중복제거·정렬 → 리포트
```

LLM에게 전체 근거를 다시 주면서 "안 버리고 요약해"라고 하지 않는다. 무엇을 버릴지가
통제되지 않기 때문이다.

map 출력 형식:

```json
[{"event": "묘 이장 작업을 진행함", "segments": [165, 166, 167, 168]}]
```

`actors`·`location`·`salience`는 **넣지 않는다.** 최종 출력 계약에 필요 없고
실패 표면만 늘린다. 필요해지면 그때 등록하고 추가한다.

### 1-2. 판정은 코드가 한다

검증자가 모델이면 검증자도 같이 무너진다. `validate_events`가 사유별로 거른다.

| 사유 | 조건 |
|---|---|
| `empty_event` | 서술 공백 |
| `no_segments` | 근거 없음 |
| `seg_out_of_range` | 담당 구간 밖 번호 |
| `foreign_language` | `common.is_corrupted_caption` — 한자·가나 이탈 |

거른 것은 사유와 함께 산출물에 남긴다. 무엇이 왜 빠졌는지 모르면 커버가 낮을 때
원인을 못 찾는다.

### 1-3. 국소 재생성

유효 사건이 **0건인 청크만** 다시 만든다. 전체 재생성 금지.

### 1-4. 빼는 것

- **`no_repeat_ngram_size=12` 제거.** 발동 2건 중 2건이 중국어 이탈로 끝났다.
  12토큰 반복 금지는 "…모습이 보입니다"처럼 구조를 정당하게 공유하는 한국어
  리포트를 분포 밖으로 민다.
- **인용 상한 8개 규칙 제거.** reduce가 사라지므로 적용 지점이 없다.
- **문장 반복 루프 감지 제거.** 병합이 코드에서 되므로 같은 서술은 구조적으로 합쳐진다.

### 1-5. 바꾸지 않는 것

분할 크기 60 · 겹침 5 · 리포트 모델 7B · 최종 출력 계약(`sentences[].text/cites`).
M9가 그 계약을 소비하므로 유지한다.

## 2. 무엇으로 재는가 — 지표를 바꾼다

### 2-1. `segment coverage ≥ 0.90`을 **주 관문에서 내린다**

이 지표는 **구간 번호를 많이 넣을수록 오른다.** 실제로 "한 문장에 70구간 인용,
본문 20자"가 이 지표에서는 좋아 보였다. 좋은 요약이 영상의 90% 구간을 반드시
언급해야 한다는 근거도 없다 — 같은 장면이 5분 이어지는 영상이면 오히려 나쁜 요약이다.

**`segment coverage`는 계속 기록하되 참고 지표로 내린다.**

### 2-2. 새 주 지표 — Event Recall

사람이 쓴 **사건 목록(event inventory)**을 정답으로 둔다. 완성된 요약문이 아니라
목록이다 — 표현 자유도가 커서 문장 단위 정답은 못 만든다.

```
E1  00:00–00:35  현장 도착
E2  00:40–01:10  관계자와 대화
E3  01:15–02:20  묘 이장 작업
```

각 사건에 근거 구간을 붙인다. **작성은 사용자가 한다**(GT 규칙 — 검색·리포트 결과를
보지 않고 프레임 실물로만).

| 지표 | 정의 | 방향 |
|---|---|---|
| **Event Recall** (주) | 정답 사건 중 리포트가 담은 비율 | 높을수록 |
| Groundedness | 인용 구간이 실제 근거인가 (M9 judge) | 높을수록 |
| Redundancy | 같은 정답 사건을 여러 문장이 중복 서술한 비율 | 낮을수록 |
| Compression | 리포트 문장 수 / 정답 사건 수 | 1에 가까울수록 |
| **Catastrophic failure** | 다른 언어 이탈·조기 종료·반복 루프 발생 영상 수 | **0이어야 한다** |

### 2-3. 관문 (결과 보기 전 확정)

| 관문 | 기준 |
|---|---|
| **C1** | Catastrophic failure **0편** |
| **C2** | Event Recall 중앙값 ≥ **0.70** |
| **C3** | Compression ≤ **2.0** (정답 사건 하나를 두 문장 넘게 쓰지 않는다) |

**주 지표는 Event Recall 중앙값.** 평균이 아니라 중앙값을 쓰는 이유는 영상 간
편차가 크다는 것이 이미 실측됐기 때문이다(±48%p).

**"전 영상이 기준을 넘어야 한다"는 규칙은 쓰지 않는다.** n이 작을 때 지나치게
brittle하다 — 1차 등록의 G1이 그래서 무너졌다.

### 2-4. 임계의 근거가 약하다는 것을 미리 적는다

0.70 · 2.0은 외부 근거가 없다. 현행 리포트에서 역산한 것도 아니다(정답 사건 목록이
아직 없으므로 역산할 대상이 없다). **결과와 함께 이 사실을 병기한다.**
결과가 나빠도 임계를 고치지 않는다.

## 3. 표본 — 3편으로는 판정하지 않는다

일반화 단위는 영상이므로 리포트 18건은 표본 18이 아니라 **n=3**이다.

| 단계 | 표본 |
|---|---|
| 개발·디버깅 | 현재 dev 3편 |
| **구조 선택 (이 등록의 판정)** | **8~12편** |
| 최종 평가 | 별도 held-out |

**M8 표본 확대에 검색 라벨은 필요 없다.** 질의·정답 구간이 아니라 사건 목록만
있으면 된다. 새 영상을 색인하고(M1~M4) 사건 목록만 쓰면 된다.

**test 4편은 쓰지 않는다.** 리포트를 보고 구조를 고르는 것이 되기 때문이다.

장르를 일부러 흩는다 — 발화 많은/적은 영상, 반복 장면 많은 영상, 실내 작업, 야외,
인터뷰, 다큐를 섞는다. 지금 dev 3편은 야외 생존·아파트 탐방·문화 다큐다.

## 4. 판정 방법

| 비교 | 무엇을 가르나 |
|---|---|
| 현행 구조 (free-form reduce) | 기준선 |
| **새 구조 (구조화 map + 코드 병합)** | 이 등록의 대상 |

같은 영상·같은 모델·같은 분할에서 둘 다 생성해 위 지표로 비교한다.
**두 구조가 같은 GPU 실행 안에서 생성돼야 한다** — 생성 환경 효과가 섞이면
구조 효과와 구분되지 않는다(캡션 쪽에서 실측된 사고).

| 결과 | 서술 |
|---|---|
| C1~C3 통과 + Event Recall이 기준선보다 높음 | 새 구조 채택 |
| C1~C3 통과, Event Recall 동등 | **안정성만 개선**으로 적는다(요약 품질 개선 아님) |
| C1 실패 | 미채택. 어떤 실패가 남았는지 기록 |

## 5. 이 문서의 한계

- 임계 0.70·2.0에 외부 근거가 없다(§2-4)
- Event Recall 판정을 사람이 할지 judge 모델이 할지 아직 안 정했다. judge를 쓰면
  **judge 자체를 먼저 검증**해야 한다 — M9에서 판정자가 고장나 있던 전례가 있다
- 사건 목록 작성자가 한 명이다. 작성자 간 일치도를 못 잰다
- 새 구조가 7B에서 JSON을 안정적으로 낼지는 아직 모른다. dev 3편 예비 실행으로
  먼저 확인하고, 실패율이 높으면 그 사실을 결과에 적는다
